# External streaming benchmark audit

Status: complete, read-only source audit  
Date: 2026-09-08

## Executive summary

The third-party benchmark is useful as a historical workload and as evidence that
the tested InfiniDysk revision deserved investigation. It is not a reliable current
league table.

The published run measured InfiniDysk commit
[`aa83ef3`](https://github.com/infinidysk/infinidysk/commit/aa83ef32662d84bdb59cdce41bcbe7f7ea72c5f0)
on August 28, 2026. Stable v1.3.0, released September 4, is 77 commits ahead and
contains several directly relevant streaming, cache, connection-startup, and
memory-retention changes. No current revision was rerun for this audit.

The headline InfiniDysk observations remain worth following up: 23.8 MB/s median
sequential throughput, 1.8 MB/s reported p05, 1.34-second full seek, 943 MiB median
peak RSS per item, and 393 MiB memory drift. However, the harness has confirmed
accounting and sampling defects that weaken its CPU, p05, capability, and seek
conclusions. Provider and Wi-Fi variance also exceeds many differences between
applications.

Two concrete optimization candidates still exist in current source:

1. Multipart 7z import validates second-segment geometry serially across volumes,
   creating one network-latency dependency per volume.
2. Existing installations with the disk segment cache enabled and write-behind set
   to its default of zero still perform cache-file writes in the playback read path.

Both should be measured before changing behavior. This audit found no defensible
basis for predicted percentage gains, a general buffer-size increase, or describing
the historical RSS drift as a memory leak.

## Scope and provenance

The audited benchmark source is pinned to
[`7192cab`](https://github.com/Viren070/nzb-streaming-benchmarks/tree/7192cabd85c75dab8a37fe088d747efcedb559de).
The [published results](https://github.com/Viren070/nzb-streaming-benchmarks/blob/7192cabd85c75dab8a37fe088d747efcedb559de/docs/RESULTS.md)
cover a run from 2026-08-28 17:17 UTC through 20:14 UTC. The README's older August
22 description is stale relative to that result file.

The host was native Windows 11 on a Ryzen 7 7800X3D with 32 GiB RAM and NVMe
storage. InfiniDysk was published in Release mode and its backend was exercised
directly, bypassing the frontend proxy. One Newshosting TLS provider supplied 20
connections over consumer Wi-Fi.

The benchmark itself reports 14% movement in whole-run medians and up to 55% on
individual entries between unchanged reruns. Applications were randomized, but
entire application runs were still performed sequentially rather than pairing each
corpus entry against a contemporaneous control.

No source code was changed and no NNTP, media, benchmark, or product test was run
for this audit. The exact NZBs, manifests, logs, and raw `results.json` are private
or gitignored, so the published aggregates cannot be independently recalculated.

## Historical observations

The comparable-population summary reported the following for InfiniDysk:

| Area | Published result | Interpretation |
|---|---:|---|
| Capability | 22/25 expected entries served; 6/6 refused | Three failures need reclassification before being called format gaps |
| Click to first byte | 3.03 s | 2.99 s import plus 18 ms cold open |
| Sequential throughput | 23.8 MB/s | Lowest application median in this run; provider variance is uncontrolled |
| Reported p05 | 1.8 MB/s | Generated by irregular chunk-arrival windows, not fixed one-second samples |
| Full seek | 1.34 s | Open-ended range read aborted after about 8 MB |
| Seek TTFB | 17 ms median; 28 ms worst | First response body byte, correctly measured |
| CPU | 10.8 CPU s/GiB | Numerator and delivered-byte denominator cover different work |
| Memory | 943 MiB/item; 1578 MiB peak | Real process observations, but not ownership attribution |
| Memory drift | +393 MiB; 1180 MiB after idle | High-water behavior over one run, not proof of a leak |

The 43.18-second import for `7z-split-compressed-header` is a valid outlier to
profile. Source inspection does not establish whether archive header parsing,
NNTP round trips, provider variance, or another stage dominated it.

## Confirmed benchmark defects

### 1. CPU per GiB mixes incompatible scopes

In [`run.mjs`](https://github.com/Viren070/nzb-streaming-benchmarks/blob/7192cabd85c75dab8a37fe088d747efcedb559de/src/runner/run.mjs),
CPU sampling begins before reset and import and continues through opens, sequential
reads, seeks, playback, integrity checks, and hole diagnostics. The delivered-byte
denominator includes only sequential, playback, cold-open, and warm-open bytes.

It omits five forward seeks, the backward seek, three integrity reads, probes, and
hole diagnostics. At default settings the omitted forward and backward seek volume
alone is about 48 MB per item. Failed phases can consume CPU and transfer partial
bytes while contributing no corresponding byte count.

**Effect:** CPU s/GiB is systematically inflated and unevenly amortizes fixed import
work across applications that download different amounts during the 30-second
playback phase. The raw data are unavailable, so neither the corrected values nor
rank ordering can be calculated.

**Correction:** account CPU and bytes per phase, or include every delivered byte in
the denominator, and report failed-phase partial work.

### 2. The p05 is not a fixed one-second percentile

[`timedStream()` and `windowedRates()`](https://github.com/Viren070/nzb-streaming-benchmarks/blob/7192cabd85c75dab8a37fe088d747efcedb559de/src/runner/measurements.mjs)
record samples only when a chunk arrives and at least 250 ms has passed. There is
no timer-driven zero sample during a stall and no initial zero sample. The window
search accepts at least 500 ms and may span much longer gaps.

A four-second no-data interval therefore does not produce four zero-rate seconds;
it can become one long averaged interval. The resulting p05 is neither a fixed
one-second distribution nor time-weighted.

**Effect:** stalls are smoothed and underrepresented. This does not show that
InfiniDysk's 1.8 MB/s result is artificially low; the defect can instead conceal
the severity and duration of stalls.

**Correction:** sample cumulative bytes on a monotonic fixed timer, emit zeros for
no-progress intervals, and define percentile window boundaries explicitly.

### 3. Playback does not simulate buffer depletion

[`measurePlayback()`](https://github.com/Viren070/nzb-streaming-benchmarks/blob/7192cabd85c75dab8a37fe088d747efcedb559de/src/runner/measurements.mjs)
drains data as fast as possible for 30 seconds. The 25 Mbps target only sets a
threshold and initial buffer target. “Seconds below bitrate” sums low-rate intervals
without subtracting consumption from bytes accumulated in faster intervals.

**Effect:** p05 below the target bitrate is not proof that a player froze, and the
reported below-bitrate duration is not a rebuffering model.

**Correction:** model a playback reservoir over time and report startup delay,
minimum reservoir, rebuffer count, and rebuffer duration.

### 4. Failed phases can retain an overall `ok` status

The `step()` helper in
[`run.mjs`](https://github.com/Viren070/nzb-streaming-benchmarks/blob/7192cabd85c75dab8a37fe088d747efcedb559de/src/runner/run.mjs)
turns phase exceptions into `{ error }`, but the item is later assigned `status =
'ok'` after the performance phases. The renderer's capability scoring uses this
overall status while metric summaries separately discard missing or non-finite
values.

Published rows such as `rar-identity-grouped` and `7z-header-encrypted` can
therefore show `ok` while lacking sequential or playback measurements.

**Effect:** capability success does not guarantee that the measured stream phases
succeeded, and the sample population can differ by metric despite the report's
broad “same 17 entries” language.

**Correction:** define required phases per capability, propagate phase failure into
item status, and publish `n`, exclusions, and error count for every metric.

### 5. Seek semantics and aggregation do not match the description

[`measureSeeks()`](https://github.com/Viren070/nzb-streaming-benchmarks/blob/7192cabd85c75dab8a37fe088d747efcedb559de/src/runner/measurements.mjs)
passes an 8 MB client-side limit without an HTTP range end. The HTTP helper therefore
sends `Range: bytes=start-` and aborts the response after approximately 8 MB. It is
not a bounded 8 MB range request.

The backward seek is stored separately, but median, worst, failures, and the report
renderer aggregate only the forward points. The advertised backward workload is
absent from headline seek values.

**Effect:** the result validly probes open-ended seek startup, transfer, and client
disconnect handling, but cannot be generalized to bounded ranges. InfiniDysk's
finite-range scheduling path specifically requires a known range end, so this
workload does not exercise it.

**Correction:** report bounded and open-ended/disconnect seeks separately and
include backward seeks in a clearly named aggregate.

### 6. Timeouts do not reliably stop work

`timedStream()` checks its deadline only when chunks arrive; it has no abort timer
for a request stalled between chunks. Item-level `withTimeout()` races a timer
against the work without cancelling the losing task.

**Effect:** a stalled request can exceed a nominal phase limit, and timed-out work
can continue into later items, affecting CPU, provider connections, and process
state. There is no evidence that this definitely changed a particular published
row.

**Correction:** use `AbortController` at both phase and item scope, await cleanup,
and verify that no requests or child work survive before the next item.

### 7. The raw row is not a transport ceiling

The [`raw` adapter](https://github.com/Viren070/nzb-streaming-benchmarks/blob/7192cabd85c75dab8a37fe088d747efcedb559de/src/adapters/raw.mjs)
is a distinct JavaScript implementation. It issues one BODY command at a time per
connection, accumulates article data with `Buffer.concat`, waits for a whole article
before decoding, and uses a scalar
[yEnc decoder](https://github.com/Viren070/nzb-streaming-benchmarks/blob/7192cabd85c75dab8a37fe088d747efcedb559de/src/nntp/yenc.mjs).
Its CPU and RSS also include the harness HTTP client, orchestration, and sampler.
For archives it commonly streams an outer volume rather than equivalent assembled
inner-file ranges.

AIOStreams reaching 48.0 MB/s while raw reported 25.8 MB/s already disproves a
universal 25.8 MB/s ceiling.

**Correction:** describe raw as a useful retrievability/control implementation, not
a numerical network limit. A transport ceiling needs equivalent article positions,
concurrency, decoding, output bytes, and process accounting.

### 8. Byte identity is consensus, not ground truth

The report groups integrity hashes by requested start offset and chooses the largest
agreement of at least two applications. Offsets are derived from each application's
reported file length, selected archive members may differ, and ties have no explicit
ambiguity rule.

**Effect:** InfiniDysk's one differing sample on `rar-named-small` is unresolved and
must not be dismissed, but consensus alone does not prove which bytes are correct.

**Correction:** pin the canonical archive member, expected length, absolute byte
ranges, exact byte counts, and independently generated expected hashes.

## Capability findings need reclassification

The published “22/25” summary labels three expected-to-serve failures as capability
gaps, but their actual errors do not establish three unsupported formats:

| Entry | InfiniDysk error | What is established |
|---|---|---|
| `rar-hdrenc-small` | `No importable media files found.` | Media discovery/importability failed; header-decryption support was not isolated |
| `rar4-stored` | Decoded yEnc CRC `2ebc210a` differed from trailer `39ab5444` | InfiniDysk enforced transport integrity; unsupported RAR4 was not demonstrated |
| `7z-obfuscated-large` | Provider returned 430 for a named article | An upstream article was missing during this run; 7z parsing was not reached conclusively |

The same `7z-obfuscated-large` message ID was missing for `nzbdav` and `nzbdavex`.
AltMount also reported repeated yEnc CRC mismatch for `rar4-stored`. The harness raw
decoder parses the trailer CRC string but does not compute or validate decoded CRC,
so raw success proves retrieval, not byte integrity.

Likewise, InfiniDysk's refusals need precise wording:

- `damaged-severe` was refused after a 430 missing-article response. This is a valid
  refusal but does not independently prove severe-damage classification logic.
- `dead-post` was refused because an important file had missing segments across all
  providers, matching the intended condition.
- `incomplete-archive-set` was refused as unsupported compression. It does not prove
  detection of the corpus's intended missing-volume condition.

Other applications succeeding does not by itself prove that they selected the same
member, requested and validated the same articles, or enforced the same CRC policy.
A future capability matrix should separate format support, file selection, article
availability, integrity policy, and intended rejection reason.

## Product changes after the measured revision

Stable v1.3.0 includes relevant changes that make the August numbers stale:

- [#1289](https://github.com/infinidysk/infinidysk/pull/1289): pipelined warm reads
  use disk cache and repair patches instead of redownloading articles.
- [#1290](https://github.com/infinidysk/infinidysk/pull/1290): trusted ranged
  playback can start without draining the entire first article.
- [#1291](https://github.com/infinidysk/infinidysk/pull/1291): pipelined completion,
  priority, and batch-resource lifecycle cleanup.
- [#1299](https://github.com/infinidysk/infinidysk/pull/1299): bounded-capacity
  segment-buffer retention became the default. This does not guarantee lower RSS.
- [#1322](https://github.com/infinidysk/infinidysk/pull/1322): segment disk cache is
  disabled on fresh installations while preserving existing-install behavior.
- [#1324](https://github.com/infinidysk/infinidysk/pull/1324): long reads expand
  provider connections sooner.
- [#1330](https://github.com/infinidysk/infinidysk/pull/1330): best-effort read-start
  connection prewarming became enabled by default.
- [#1325](https://github.com/infinidysk/infinidysk/pull/1325): bounded cache
  write-behind became available, though zero/inline remains the default when the
  cache is enabled.
- [#1292](https://github.com/infinidysk/infinidysk/pull/1292): a finite-range
  scheduler canary was added and remains disabled by default.

These changes target mechanisms implicated by the historical results, but they are
not evidence of a particular current throughput or memory improvement without a
rerun.

## Remaining optimization opportunities

### Priority 1: parallelize multipart 7z geometry validation

[`SevenZipProcessor.GetMultipartFile()`](../../backend/Queue/FileProcessors/SevenZipProcessor.cs)
first resolves missing file sizes with bounded queue concurrency, then iterates
sorted volumes and awaits `ProbeSecondSegmentRangeAsync()` one at a time.

[`NzbFile.ProbeSecondSegmentRangeAsync()`](../../backend/Models/Nzb/NzbFile.cs)
may request yEnc headers for the second segment to validate uniform-size geometry.
Each volume is independent during validation; only the final prefix-sum offsets need
ordered assembly.

**Hypothesis:** many-volume 7z imports accumulate one provider round trip per volume
on the critical path.

**Smallest discriminating check:** add stage timing and request counts around size
resolution, second-segment probes, archive enumeration, and header decode for the
43.18-second class of input. Compare current serial validation with bounded parallel
validation using the existing exact queue-concurrency policy. Preserve all geometry
validation and assemble offsets in volume order after all probes complete.

**Risk:** aggressive parallelism can compete with active streams and provider limits.
This is a bounded queue-operation optimization, not a reason to skip validation.

### Priority 2: remove inline disk latency from cache-enabled playback

[`SegmentCacheNntpClient`](../../backend/Clients/Usenet/SegmentCacheNntpClient.cs)
uses bounded write-behind only when configured. Otherwise
`ValidatedCacheWriteStream.ReadAsync()` awaits the temporary cache-file write before
returning each source read, and completion synchronously flushes and publishes cache
metadata.

Fresh installations now default the segment cache off, but upgraded installations
preserve the old enabled state. With cache enabled, write-behind defaults to zero.
The existing implementation and tests already support a controlled comparison,
including [blocked persistence](../../tests/NzbWebDAV.Tests/Clients/Usenet/SegmentCacheNntpClientTests.cs#L417)
and [byte-budget pressure](../../tests/NzbWebDAV.Tests/Clients/Usenet/SegmentCacheNntpClientTests.cs#L492).

**Hypothesis:** inline cache persistence lowers throughput or deepens stalls when the
cache volume is slow or contended.

**Smallest discriminating check:** on the target deployment, replay the same article
set with cache disabled, cache enabled/inline, and cache enabled with a bounded
write-behind budget. Record response-byte timing, cache hits, skipped writes, disk
latency, memory, and hash validation. A safe rollout must retain backpressure and
skip caching rather than make playback wait when the byte budget is exhausted.

### Priority 3: compare bounded and open-ended seek scheduling

The benchmark's `Range: bytes=start-` requests intentionally leave
[`RangeContext`](../../backend/WebDav/Requests/RangeContext.cs) without a finite read
budget. [`GetAndHeadHandlerPatch`](../../backend/WebDav/Base/GetAndHeadHandlerPatch.cs)
sets a budget only when the range end is known, while
[`BaseStoreStreamFile`](../../backend/WebDav/Base/BaseStoreStreamFile.cs) installs the
scheduler context only when the finite-range canary is enabled.

**Hypothesis:** bounded player seeks may benefit from the finite scheduler, while the
benchmark's open-ended abort pattern exercises a different and still relevant path.

**Smallest discriminating check:** interleave equivalent bounded 8 MiB ranges and
open-ended ranges aborted after 8 MiB, with the canary off and on. Measure TTFB,
time to 8 MiB, articles requested beyond the consumed range, connection reuse after
disconnect, and provider error rate. Do not infer that a larger static batch width is
better; current scheduling already includes adaptive width and memory budgets.

### Priority 4: attribute memory before tuning retention

Current startup caps idle segment-pool capacity at half of the article admission
budget, clamped to 32–256 MiB in
[`ConfigureSegmentBufferPool()`](../../backend/Program.cs). The article budget uses
25% of the managed-heap ceiling within configured bounds and is admission control,
not eager allocation. Shared streams additionally have bounded entry/ring limits and
a grace period.

Current diagnostics expose owned article leases, decoded pipes, checked-out and idle
pool capacity, shared-ring/scratch capacity, cache writer state, GC metrics, and RSS
through `/api/memory-components`. Some component values overlap and must not be
summed.

**Hypothesis:** the historical 943 MiB median peak combines live article work,
retained pool capacity, shared stream rings, cache activity, runtime heap policy, and
process high-water behavior rather than one unbounded owner.

**Smallest discriminating check:** capture the effective streaming configuration and
memory-component snapshots before each item, at peak, after readers detach, after the
shared-stream grace period, and after a documented idle interval. Record GC committed
bytes, working set/RSS, active article count, pooled idle capacity, shared entries,
and cache mode. Compare retention policies only after ownership is established.

### Priority 5: measure legacy metadata seek cost separately

Trusted exact segment metadata now permits direct ranged startup. Legacy or
untrusted metadata can still use a seek path in
[`NzbFileStream`](../../backend/Streams/NzbFileStream.cs) that drains the target
article tail before returning data.

**Hypothesis:** old imports without trusted geometry retain slower seek behavior even
when newly imported files do not.

**Smallest discriminating check:** run the same bounded seeks against newly imported
trusted metadata and a migrated legacy record, recording first requested article,
bytes fetched before first response byte, and resulting metadata trust. If confirmed,
prefer a safe metadata refresh path over weakening range validation.

## Recommended rerun design

1. Pin the current release commit, effective InfiniDysk configuration, provider
   account limits, OS/runtime, and cache volume characteristics.
2. Fix CPU byte accounting, fixed-time sampling, cancellation, phase status, and
   backward-seek aggregation before comparing applications.
3. Publish sanitized per-phase raw results, request traces, exclusions, sample counts,
   and exact harness revision so aggregates are reproducible without exposing NZBs.
4. Pair or interleave each application and raw-control entry instead of running one
   complete application at a time. Repeat across multiple time windows.
5. Report bounded HTTP ranges separately from open-ended ranges with client aborts.
6. Use a reservoir-based playback model and retain raw time series so stalls can be
   inspected directly.
7. Establish canonical member identity, expected length, independent hashes, and CRC
   policy before scoring byte correctness or format capability.
8. For InfiniDysk, A/B serial versus bounded 7z validation, cache off/inline/bounded
   write-behind, finite scheduling off/on, and trusted versus legacy metadata.
9. Capture `/api/memory-components` and effective configuration alongside RSS; avoid
   adding overlapping ownership counters.
10. Treat differences below the benchmark's own observed variance as unresolved until
    repeated runs establish confidence intervals.

## Conclusion

The benchmark found real historical symptoms, especially weak sustained delivery on
its workload, slow multipart imports, and a large memory footprint. Its strongest
value is as a corpus and experiment generator, not as proof of current relative
performance.

The first product experiment should instrument and then bound-parallelize multipart
7z geometry probes if they dominate import latency. The second should compare inline
and bounded cache persistence on cache-enabled upgrades. In parallel, the harness
needs corrected CPU accounting, timer-based rate sampling, cancellable work, explicit
phase success, and distinct bounded/open-ended seek reports. Until those changes and
a current paired rerun exist, neither application rankings nor quantified improvement
claims are supported.
