## 1. Building blocks

### 1.1 Queue pipeline (`backend/Queue/`)

- **`QueueManager.cs`** (`backend/Queue/QueueManager.cs:12`) — singleton, started from its own constructor (`_ = ProcessQueueAsync(...)` at `QueueManager.cs:36`), not an `IHostedService`. Runs a `while` loop (`QueueManager.cs:78`) that:
  1. Pulls the single highest-priority, oldest, not-paused `QueueItem` via `dbClient.GetTopQueueItem` (`DavDatabaseClient.cs:121-155`, ordered `Priority desc, CreatedAt asc`, filtered on `PauseUntil == null || now >= PauseUntil`).
  2. If nothing to do, sleeps 1 minute or until woken via `AwakenQueue()` (`QueueManager.cs:44-54`, used e.g. after a `PauseUntil` is set, so retries don't wait the full minute).
  3. Creates one `ArticleCachingNntpClient` scoped to just that item (`QueueManager.cs:113`) and runs `QueueItemProcessor.ProcessAsync()` to completion before looping.
  4. A `SemaphoreSlim(1,1)` (`_semaphore`, `QueueManager.cs:18`) guards all mutations of `_inProgressQueueItem`, used so `RemoveQueueItemsAsync` can safely cancel the in-flight item if the user removes it from the UI.
  - **Processing is strictly one queue item at a time.** This is the single biggest throughput constraint in the whole ingestion path (see Weak points, QS-2/QS-3).

- **`QueueItemProcessor.cs`** (`backend/Queue/QueueItemProcessor.cs:24`) — orchestrates one item end-to-end:
  1. Duplicate-nzb check (`GetMountFolder`, `QueueItemProcessor.cs:244`) against `duplicate_nzb_behavior` config (`mark-failed` / `increment` / default-overwrite).
  2. `NzbDocument.LoadAsync` (streaming XML parse, see 1.4) + archive-password resolution: filename override takes priority over the NZB's own `password` meta tag (`QueueItemProcessor.cs:121`, fork-added by Root-Core PR #215, upstream).
  3. **Deobfuscation steps 1–3** (see 1.2).
  4. **File processing** (`GetFileProcessors`, `QueueItemProcessor.cs:209`) — groups `FileInfo`s by archive kind (7z / rar / multipart-mkv / other) and dispatches to the matching processor, run with **bounded concurrency** = `GetMaxDownloadConnections() + 5` (`QueueItemProcessor.cs:148`, via `WithConcurrencyAsync` in `backend/Extensions/IEnumerableTaskExtensions.cs:65` — outside my scope but the touchpoint matters: within a single queue item, file-level work IS parallelized; it's only cross-item processing that's serial).
  5. Optional step-3 **full article existence check** (`CheckAllSegmentsAsync`) gated by an `ensure_article_existence` per-category config (`QueueItemProcessor.cs:156-174`) — this is the "verify every segment exists before declaring success" health gate; expensive, so opt-in per category.
  6. **Aggregation + post-processing**, all inside one `MarkQueueItemCompleted` closure (`QueueItemProcessor.cs:177-206`) that is the actual DB-write boundary (see 2).
  - Retry/failure semantics are three-way (`QueueItemProcessor.cs:44-90`):
    - Cancellation (item removed mid-flight) → clear change tracker, no history entry.
    - `IsRetryableDownloadException()` → set `PauseUntil = now + 1min`, keep the item queued, log and move on (this is the backoff mechanism referenced in CLAUDE.md).
    - Any other exception → `MarkQueueItemCompleted(error: e.Message)`, moves item to `HistoryItems` as `Failed`.

- **Deobfuscation steps** (`backend/Queue/DeobfuscationSteps/`), run once per NZB, not per queue-item-processor-instance:
  1. **`FetchFirstSegmentsStep`** (`.../1.FetchFirstSegment/FetchFirstSegmentsStep.cs:14`) — downloads only the *first article* of every file in the NZB (bounded concurrency, same `+5` pattern), reads up to 16KB, extracts yEnc header + RAR4/RAR5 magic-byte detection. This is the core obfuscation-busting trick: real filenames/order are recoverable from a tiny fraction of the total download.
  2. **`GetPar2FileDescriptorsStep`** (`.../2.GetPar2FileDescriptors/GetPar2FileDescriptorsStep.cs:11`) — finds the smallest file carrying PAR2 magic bytes among the first-segments, downloads *that whole file* (it's small, PAR2 index files are typically KB–low-MB), and parses `FileDesc` packets out of it via `Par2.ReadFileDescriptions` (see 1.3) to recover original filenames + declared file sizes + 16K-hashes.
  3. **`GetFileInfosStep`** (`.../3.GetFileInfos/GetFileInfosStep.cs:13`) — reconciles three name sources (PAR2 descriptor name, NZB `subject` line, yEnc header name) with a priority scheme that penalizes obviously-obfuscated or missing names (`GetFilenamePriority`, `GetFileInfosStep.cs:72`) and cross-validates PAR2 file-size claims against actual yEnc-declared size (`IsCloseToYencodedSize`, `GetFileInfosStep.cs:98`, 95%–100% tolerance band) to avoid mis-matching a PAR2 descriptor to the wrong file when there are hash collisions.

- **File processors** (`backend/Queue/FileProcessors/`), one per grouped file-type, all subclass `BaseProcessor` (`BaseProcessor.cs:7`, a `ProcessAsync()`/`ProcessAsync(IProgress<int>)` template pair — overriding both is explicitly disallowed by contract, only one):
  - **`RarProcessor`** (`RarProcessor.cs:13`) — opens a live NZB-backed stream (no download-to-disk), parses RAR headers via `SharpCompress` (`RarUtil.GetRarHeadersAsync`), and emits one `StoredFileSegment` per file-within-archive with byte ranges *inside the still-undownloaded RAR part*, AES params if password-protected, and a `PartNumber` resolved from either RAR headers or filename patterns (`.partNN.rar`, `.rNN`, bare `.rar`) with a delta-reconciliation step in the aggregator for when the two disagree.
  - **`SevenZipProcessor`** (`SevenZipProcessor.cs:15`) — stitches multi-part `.7z.001…` files into one logical `MultipartFileStream`, parses 7z entries, **hard-rejects compressed or solid+encrypted 7z archives** (`Unsupported7zCompressionMethodException`, `NonRetryableDownloadException` at `SevenZipProcessor.cs:53-61`) — only uncompressed (store-mode) 7z is supported. Uses `InterpolationSearch` (`SevenZipProcessor.cs:158`) to map each 7z entry's byte range onto the underlying multipart file's byte ranges without a linear scan.
  - **`MultipartMkvProcessor`** (`MultipartMkvProcessor.cs:10`) — handles releases that split a raw `.mkv` into sequential unarchived parts (`.mkv.001`, `.mkv.002`, …) with no compression/container at all — just concatenation.
  - **`FileProcessor`** (`FileProcessor.cs:10`) — the fallback for plain, non-archived files; on a missing-article error it silently drops the file *unless* it's a video file (`FileProcessor.cs:33`), on the theory that missing PAR2/sample/nfo files shouldn't fail the whole release but a missing video should surface.

- **Aggregators** (`backend/Queue/FileAggregators/`), one per processor type, all subclass `BaseAggregator` (`BaseAggregator.cs:7`) which provides shared directory-materialization logic (`EnsureParentDirectory`/`EnsureDirectory`, with an in-memory `_directoryCache` per aggregator instance to avoid re-creating the same `DavItem` directory twice within one queue item, `BaseAggregator.cs:40-61`). Each aggregator converts one processor's `Result`s into `DavItem` + blob rows:
  - **`RarAggregator`** (`RarAggregator.cs:11`) groups `StoredFileSegment`s by in-archive path, validates all volumes are present and consistent (`ValidateVolumes`, throws `InvalidDataException` on missing/inconsistent volumes — a data-integrity gate that fails the whole item rather than serving a truncated file), resolves part ordering via a header-vs-filename delta heuristic, and — notably — **renames the sole extracted file to match the release folder name if it's a single-file archive with an obfuscated name** (`RarAggregator.cs:52`), which is a deliberate UX/Sonarr-matching decision.
  - **`FileAggregator`** (`FileAggregator.cs:8`) is the simple case: one `DavNzbFile` (just a `SegmentIds` array) per plain file.
  - **`SevenZipAggregator`** / **`MultipartMkvAggregator`** mirror `RarAggregator` for their respective processor outputs, both ultimately producing `DavMultipartFile` rows.
  - All aggregators run inside the *same* `MarkQueueItemCompleted` transaction closure and are unconditionally invoked in sequence (`QueueItemProcessor.cs:182-185`) — each just filters `processorResults` with `OfType<T>`, so this is effectively a manual discriminated-union dispatch rather than true polymorphism.

- **Post-processors** (`backend/Queue/PostProcessors/`), run in a fixed order after aggregation, all operating on the **EF change-tracker's `Added` `DavItem` entries** (not yet persisted) so they can rename/remove/validate before the transaction ever hits disk:
  1. `RenameDuplicatesPostProcessor` (`RenameDuplicatesPostProcessor.cs:7`) — disambiguates same-named siblings ("`name (2).ext`") since `DavItems` has a unique `(ParentId, Name)` index (`DavDatabaseContext.cs:141`).
  2. `SampleFilePostProcessor` — optionally strips sample video files (or fails the release if it's sample-only), gated by `exclude_sample_files` config; **this is the one habenspass-authored logic change in this whole domain** (commit `557eac1`, "sample file rejection").
  3. `BlocklistedFilePostProcessor` (`BlocklistedFilePostProcessor.cs:9`) — glob-style (`*` → `.*`) case-insensitive filename blocklist, removes matches via `DavItemRemover.Remove` (which also deletes the pending in-memory blob entry, `DavItemRemover.cs:10`).
  4. `EnsureImportableVideoValidator` (`EnsureImportableVideoValidator.cs:9`) — optionally throws `NoVideoFilesFoundException` if, after all the above, no video file survived — this is what turns a "release with only samples/junk" into a failed history entry instead of a silently-empty folder.
  5. `CreateStrmFilesPostProcessor` (`CreateStrmFilesPostProcessor.cs:11`) — optional (`import_strategy == "strm"`), writes `.strm` files to a real filesystem path outside the DB-backed virtual tree, each containing a signed download URL (`GenerateDownloadKey`) — this is the one place in this domain that touches the *real* filesystem rather than the SQLite-backed virtual one.

  Note: `QueueItem.PostProcessingOption` (`QueueItem.cs:27`, `Repair`/`RepairUnpack`/`RepairUnpackDelete`/`None`) is persisted and accepted from Sonarr/Radarr via the SABnzbd-compatible API, but **nothing in the pipeline branches on it** (`grep` confirms `.PostProcessing` is only ever set, never read, outside the EF column mapping) — the pipeline always fully deobfuscates+aggregates+post-processes regardless of what the Arr client requested. Likely vestigial SAB-API-compatibility surface.

### 1.2 Virtual filesystem model (`backend/Database/Models/`)

- **`DavItem`** (`DavItem.cs:6`) is the single tree node type for the whole virtual filesystem — directories and files alike, discriminated by `Type` (`Directory`/`UsenetFile`) and a finer `SubType` enum (`Directory`, `WebdavRoot`, `NzbsRoot`, `ContentRoot`, `SymlinkRoot`, `IdsRoot`, `NzbFile`, `RarFile`, `MultipartFile`). Both enums carry an explicit comment that their numeric values are load-bearing and must never be renumbered without a migration (`DavItem.cs:63-64, 88-89`) — SQLite stores the raw int.
  - Five singleton static instances (`Root`, `NzbFolder`, `ContentFolder`, `SymlinkFolder`, `IdsFolder`, `DavItem.cs:90-144`) with hardcoded all-zero-except-last-nibble GUIDs — these never round-trip through the DB as real rows; they're synthetic roots the WebDAV layer special-cases.
  - `Path` is a denormalized, eagerly-maintained materialized path string (`DavItem.New`, `DavItem.cs:51`: `Path.Join(parent.Path, name)`), not derived at read time from parent-chain walks — trades a bit of write-time bookkeeping (and a rename cascade problem, see Weak points) for O(1) path reads everywhere (WebDAV path resolution, `.strm` generation, rclone-forget path computation).
  - Actual per-file segment/byte-range metadata (the potentially-large part) is **not stored in this table** — only a `FileBlobId` (and, historically, `NzbBlobId`) pointer into the blob store (see 1.3 below). `DavItem` itself stays small and uniformly-shaped regardless of whether the underlying file has 1 segment or 5,000.
  - Indexes (`DavDatabaseContext.cs:141-153`) are tuned for the two real hot paths: single-name lookup under a parent (`(ParentId, Name)` unique — this *is* directory listing/resolution) and health-check scheduling (`(Type, HistoryItemId, NextHealthCheck, ReleaseDate, Id)`).

- **Blob-store split** — this is the most important architectural finding in the Database scope. `DavNzbFile`/`DavRarFile`/`DavMultipartFile` (`DavNzbFile.cs`, `DavRarFile.cs:7`, `DavMultipartFile.cs:7`) are all `[MemoryPackable]` and *also* have full EF Core entity configs with a JSON-string `ValueConverter` (`DavDatabaseContext.cs:156-228`) mapping them to `DavNzbFiles`/`DavRarFiles`/`DavMultipartFiles` SQLite tables — **but grepping the entire backend for `.NzbFiles.Add(`, `.RarFiles.Add(`, `.MultipartFiles.Add(` returns zero hits.** Every aggregator instead does `dbClient.Ctx.BlobNzbFiles.Add(...)` / `BlobRarFiles.Add(...)` / `BlobMultipartFiles.Add(...)` — plain `List<T>` fields on the context (`DavDatabaseContext.cs:49-51`), which `DavDatabaseContext.SaveChangesAsync` (`DavDatabaseContext.cs:613-651`) writes out via `BlobStore.WriteBlob<T>` **before** calling `base.SaveChangesAsync`, as zstd-compressed (`CompressionLevel = 1`) MemoryPack-serialized files under `CONFIG_PATH/blobs/<guid[0:2]>/<guid[2:4]>/<guid>` (`BlobStore.cs:12-19`, 2-level sharded flat-file layout to avoid huge single directories). The SQLite JSON-table code paths are read-fallback-only (`DavDatabaseClient.GetDavNzbFileAsync` etc., `DavDatabaseClient.cs:72-118`: try blob store first, fall back to the SQLite table) and are kept alive by a dedicated startup-run `UsenetFileToBlobstoreMigrationService` (`backend/Services/UsenetFileToBlobstoreMigrationService.cs:14`, outside my scope but directly explains this table's purpose) that lazily drains any pre-migration rows out of SQLite into blob files and deletes them, a few at a time, every process start, until the tables are empty. **This confirms a deliberate, already-completed architectural migration** (git-dated 2026-01-19, `8b0fd2e`/`d2cee00`, both nzbdav-dev/INHERITED) from "store per-segment metadata as JSON in SQLite rows" to "store it in flat compressed files, keep only a GUID pointer in SQLite" — almost certainly to keep the SQLite file itself small and its write-ahead-log churn low regardless of how many segments a release has (a multi-GB remux can have 5,000+ segments; as JSON that's a large TEXT column value on every insert/update).

- **`QueueItem`** (`QueueItem.cs:3`) / **`HistoryItem`** — SABnzbd-shaped queue/history rows. Priority ordering + `PauseUntil` backoff live here (`QueueItem.PauseUntil`, consumed by `GetTopQueueItem`, `DavDatabaseClient.cs:131`).
- **`QueueNzbContents`** — the same SQLite-fallback-with-blob-store-primary pattern as above, but for the *raw .nzb XML itself*: `GetTopQueueItem` (`DavDatabaseClient.cs:136-151`) tries `BlobStore.ReadBlob(queueItem.Id)` first and only queries `QueueNzbContents` (a `TEXT` column holding the whole NZB XML) if that misses.
- **`NzbName`** — small dedicated table (fork-adjacent to the `NzbBlobId`/`NzbBlobCleanupItem` migration `20260226053712_Add-NzbBlobId-And-NzbNames`), used to let users re-download the original .nzb for a completed/history item without needing the queue row anymore.
- **`*CleanupItem` models** (`BlobCleanupItem`, `HistoryCleanupItem`, `DavCleanupItem`, `NzbBlobCleanupItem`) are pure work-queues for their corresponding `HostedService`s in `backend/Services/` (outside scope) — e.g. `HistoryCleanupItem.DeleteMountedFiles` flag threading through from `DavDatabaseClient.RemoveHistoryItemsAsync` (`DavDatabaseClient.cs:197-227`) into a background deferred deletion, rather than deleting synchronously inline with the API call.

### 1.3 PAR2 parsing (`backend/Par2Recovery/`)

Despite the folder name, **this is not a PAR2 repair/recovery engine** — there is no Reed-Solomon reconstruction of missing data anywhere in the codebase. `Par2.cs` (`Par2.cs:9`) implements only the packet-header framing (`Par2PacketHeaderMagic = "PAR2\0PKT"`) and a single packet type, `FileDesc` (file-description packets: original filename + declared length + 16K-prefix MD5 hash), consumed exclusively by `GetPar2FileDescriptorsStep` for deobfuscation (1.1). `HasPar2MagicBytes` (`Par2.cs:116`) is used purely to *detect* "this file looks like a PAR2 index" during the first-segment scan — it never inspects recovery-slice packets. This means: if Usenet articles are missing/corrupt, NzbDav has no ability to reconstruct them from PAR2 redundancy — it can only *fail* (or, per `HealthCheckService`, flag it), never *repair*. That's a meaningful gap relative to what "PAR2" implies to most Usenet users (SABnzbd/par2cmdline-style repair).

### 1.4 NZB parsing (`backend/Models/Nzb/`)

`NzbDocument.LoadAsync` (`NzbDocument.cs:17`) uses `System.Xml.XmlReader` in streaming/forward-only mode (`Async = true`, no DOM materialization) to parse `<head>` metadata and `<file>`/`<segments>`/`<segment>` elements directly into `NzbFile`/`NzbSegment` POCOs. This matters at scale: large-season-pack or scene-collection NZBs can be tens of MB of XML with tens of thousands of `<segment>` elements; streaming parsing avoids holding a DOM tree of that size in memory just to read it once.

### 1.5 WebDAV layer (`backend/WebDav/`)

- **`DatabaseStore`** (`DatabaseStore.cs:12`) implements NWebDav's `IStore` and is the sole entry point: `GetItemAsync(path)` trims slashes and delegates to a single root `DatabaseStoreCollection` instance's `ResolvePath` — i.e., **every WebDAV path resolution is a live, uncached, segment-by-segment SQLite query chain** (`DavDatabaseClient.GetDirectoryChildAsync`, one `(ParentId, Name)` indexed lookup per path segment), not a full-tree in-memory cache.
- **`DatabaseStoreCollection`** (`DatabaseStoreCollection.cs:16`) is the generic directory node; `GetItem`/`GetAllItemsAsync` dispatch on `DavItem.SubType` (`DatabaseStoreCollection.cs:123-150`) to the specific typed wrapper (`DatabaseStoreNzbFile`/`RarFile`/`MultipartFile`/`WatchFolder`/`IdsCollection`/`SymlinkCollection`) — this switch is the de facto "type registry" for the whole virtual filesystem; adding a new `SubType` means adding a case here.
- **`DatabaseStoreWatchFolder` / `DatabaseStoreCategoryWatchFolder`** (`DatabaseStoreWatchFolder.cs:15`, `DatabaseStoreCategoryWatchFolder.cs:16`) implement the `/nzbs/<category>/` WebDAV path that some Arr setups use instead of the SABnzbd API directly. Notably, `CreateItemAsync` (`DatabaseStoreCategoryWatchFolder.cs:45`) just **constructs an `AddFileController` and an `AddFileRequest` in-process and calls the same controller method the SABnzbd HTTP API uses** (`AddFileController.AddFileAsync`) — so there is exactly one ingestion code path regardless of whether an NZB arrives via SABnzbd-API POST or WebDAV file-drop; the WebDAV side is a thin adapter, not a parallel implementation. Same pattern for delete (`DeleteItemAsync` calls `RemoveFromQueueController` directly, `DatabaseStoreCategoryWatchFolder.cs:67`).
- **`DavFileStreamFactory`** (`DavFileStreamFactory.cs:13`) is the single place that turns a `DavItem` + its blob metadata into a live, decoded/decrypted `Stream`, keyed on `SubType` (`DavFileStreamFactory.cs:24`): plain files get `usenetClient.GetFileStream(segmentIds, ...)` directly; RAR files convert their legacy `DavRarFile.RarParts` into the same `DavMultipartFile.Meta` shape (`RarFile.ToDavMultipartFileMeta()`, `DavRarFile.cs:35`) so there's one multipart-stream implementation, not two; multipart files additionally wrap in `AesDecoderStream` if `Metadata.AesParams != null`. This factory is explicitly shared between the WebDAV read path and the fork's prefetch-cache warmer (per its own doc-comment, `DavFileStreamFactory.cs:8-11`) — a deliberate single-source-of-truth for "how do we turn stored metadata into bytes."
- **`BaseStoreStreamFile`** (`Base/BaseStoreStreamFile.cs:10`) is the shared base for the three file-subtype wrappers. `GetReadableStreamAsync` (`BaseStoreStreamFile.cs:16`) first checks for a **complete local prefetch-cache file on disk** (`TryGetCachedStreamAsync`, `BaseStoreStreamFile.cs:33` — fork-specific, part of the Jellyfin-webhook episode-prefetch feature) and serves a plain `FileStream` if present (bypassing Usenet entirely for that read); otherwise it tags the request with `DownloadPriorityContext { Priority = High }` (`BaseStoreStreamFile.cs:22`) via an `AsyncLocal`-style scoped context so the shared `PrioritizedSemaphore` in the Usenet client stack (outside my scope) can prefer interactive reads over background queue downloads on the same connection pool.
- **`GetAndHeadHandlerPatch`** (`Base/GetAndHeadHandlerPatch.cs:20`) replaces NWebDav's stock GET/HEAD handler entirely. It computes `Content-Range`/`Content-Length`/206-vs-200 status purely from `stream.CanSeek`/`stream.Length` (`GetAndHeadHandlerPatch.cs:102-136`) and does the actual byte-range copy itself (`CopyToAsync`, `GetAndHeadHandlerPatch.cs:164`) via `Stream.Seek` + 64KB-buffered manual copy — i.e., **seeking to an arbitrary offset in a 20GB file is a `Stream.Seek()` call on the composed `MultiSegmentStream`/`DavMultipartFileStream`/`AesDecoderStream` chain**, not a byte-for-byte scan from offset 0. This is the mechanism that makes QS-1 (sub-2s seek) achievable at all; the actual seek performance then depends entirely on how efficiently those composed streams (Usenet client stack scope) can jump to the right article without re-downloading skipped bytes.

### 1.6 Migration gating (`Program.cs`, outside strict scope but directly cited in CLAUDE.md)

`Program.cs:61-70`: migrations only ever run when the binary is invoked with `--db-migration [targetMigration]`, never implicitly on normal startup. `BlockUpgradesToV06X` (`Program.cs:136-168`) is a hardcoded one-off hard-stop: if the DB file exists and migration `20260226053712_Add-NzbBlobId-And-NzbNames` is still pending, the process refuses to start (even to run `--db-migration`, since this check runs unconditionally before the migration-invocation branch) unless `UPGRADE=0.6.0` is explicitly set — a deliberate "this upgrade is one-way, make the user opt in with a backup warning" gate for a specific breaking schema change. This pattern (a named-migration string check + env-var acknowledgment) is reusable for future breaking migrations but is currently hardcoded to this one migration, not a general mechanism.

## 2. Key runtime interaction: NZB → virtual filesystem

```
Sonarr/Radarr POST (SABnzbd API, outside scope)  ─┐
WebDAV PUT to /nzbs/<category>/<file>.nzb        ─┼─► AddFileController.AddFileAsync (Api/, outside scope)
                                                   │      → INSERT QueueItem + write raw .nzb to blob-store
                                                   │        (QueueNzbContents as SQLite fallback)
                                                   ▼
                                          QueueManager.ProcessQueueAsync loop (serial, 1 item at a time)
                                                   │
                                                   ▼
                                   QueueItemProcessor.ProcessAsync (per item)
                                                   │
                              ┌────────────────────┼────────────────────────┐
                              ▼                    ▼                        ▼
                     duplicate-nzb check    NzbDocument.LoadAsync    archive password resolve
                              │                    │                        │
                              └────────────────────┴────────────────────────┘
                                                   ▼
                        Deobfuscation: FetchFirstSegments (bounded concurrency)
                                     → GetPar2FileDescriptors (download PAR2 index file)
                                     → GetFileInfos (reconcile names, validate sizes)
                                                   ▼
                        File processors, grouped by type, bounded concurrency
                          RarProcessor | SevenZipProcessor | MultipartMkvProcessor | FileProcessor
                                                   ▼
                        (optional) full article-existence check, if category opted in
                                                   ▼
                        MarkQueueItemCompleted { ... } closure:
                          category/mount DavItem folders created
                          RarAggregator / FileAggregator / SevenZipAggregator / MultipartMkvAggregator
                            → DavItem rows + Blob{Nzb,Rar,Multipart}Files (in-memory lists)
                          RenameDuplicatesPostProcessor
                          SampleFilePostProcessor (optional)
                          BlocklistedFilePostProcessor
                          EnsureImportableVideoValidator (optional, can throw → failure path)
                          CreateStrmFilesPostProcessor (optional)
                                                   ▼
                        dbClient.Ctx.SaveChangesAsync()
                          → BlobStore.WriteBlob<T> for each pending blob (flat files, zstd+MemoryPack)
                          → base.SaveChangesAsync (single SQLite transaction: DavItems + QueueItems delete + HistoryItems insert)
                          → RcloneVfsForget (best-effort, only if rclone remote-control enabled)
                                                   ▼
                        QueueItem removed, HistoryItem added, websocket events fired,
                        Arr client's monitored-downloads refreshed (best-effort, swallowed on error)
```

Failure/retry paths (`QueueItemProcessor.ProcessAsync`, `QueueItemProcessor.cs:35-91`):
- **Cancellation** (item removed via UI while processing) → `ClearChangeTracker()`, no history entry, no DB write at all.
- **Retryable download exception** (e.g., transient Usenet connectivity) → `PauseUntil = now + 1min`, item stays in `QueueItems`, loop picks it up again after backoff (or immediately if `AwakenQueue` is called). No cap observed on retry count — an item can retry indefinitely as long as the error stays classified retryable (see Weak points).
- **Any other exception** (including the deliberate `EnsureImportableVideoValidator` throw, `Unsupported7zCompressionMethodException`, RAR volume-consistency failures) → item removed from `QueueItems`, `HistoryItem` added with `DownloadStatus = Failed` and the exception message, Arr client sees it as a failed download via the SABnzbd history API (outside scope).

Crash-safety characteristics (QS-8): all `DavItem`/`QueueItem`/`HistoryItem` mutations for one queue item are batched into a **single `SaveChangesAsync` call** at the very end of `ProcessQueueItemAsync` (`QueueItemProcessor.cs:177-206`) — there is no partial-write window where some `DavItem`s exist but the `QueueItem` hasn't been removed yet, *except* for the blob-file writes, which happen just before the SQLite transaction (`DavDatabaseContext.cs:617-623`) and are explicitly rolled back on any exception (`DavDatabaseContext.cs:638-650`, `catch { foreach blob: BlobStore.Delete(...); throw; }`). So: kill the process before `SaveChangesAsync` returns → queue item is retried from scratch next start (all work re-downloaded, nothing partially visible in the virtual FS); kill it during the blob-write-then-SQLite-commit window → the `catch` block only runs if the *current* process is still alive to run it, so a hard kill (not a normal exception) between blob writes and the SQLite commit could leave orphaned blob files on disk with no DB row pointing at them — those would need `BlobCleanupItem`/orphan-scanning (`RemoveOrphanedFilesSchedulerService`, outside scope) to eventually reclaim. This is a plausible small leak, not a corruption risk to the visible filesystem.

## 3. Architectural decisions (tagged)

1. **SQLite as the sole datastore for the virtual filesystem tree** — INHERITED. Plausible rationale: single-file, zero-ops, trivially backed-up-by-copying-a-file datastore that fits the single-container homelab deployment target (QS-7) perfectly; EF Core gives a productive ORM without running a separate DB process.
2. **Serial (one-item-at-a-time) queue processing** — INHERITED (`QueueManager.cs:78`, present since early upstream history). Plausible rationale: Usenet download bandwidth is normally the bottleneck resource, not CPU, and a single homelab uplink can usually saturate on one release at a time anyway; serial processing also sidesteps a whole class of concurrent-SQLite-write and shared-connection-pool contention problems for comparatively little throughput gain in the common case.
3. **Blob-store split for per-segment metadata (flat files, MemoryPack+zstd) instead of SQLite JSON columns** — INHERITED, and itself a *migration away from* an earlier INHERITED decision (the JSON-in-SQLite tables `DavNzbFiles`/`DavRarFiles`/`DavMultipartFiles` are the previous design, now legacy-read-only, actively drained by `UsenetFileToBlobstoreMigrationService`). Rationale: keeps the SQLite file itself small and its per-row size bounded regardless of segment count, at the cost of a second storage subsystem (flat files) that must be kept consistent with SQLite (see Weak points).
4. **Denormalized materialized `Path` on `DavItem`** — INHERITED. Rationale: O(1) path reads for WebDAV/rclone/strm-generation, at the cost of needing to keep it in sync on rename (only ever mutated for the specific rename it was designed for — `RenameDuplicatesPostProcessor` — not a generic "move directory" cascade, see Weak points).
5. **Deobfuscation via first-segment + PAR2-descriptor sniffing before downloading whole files** — INHERITED. Rationale: makes ~all of the file-identification/naming work possible with a tiny fraction of the total NZB's bytes, directly serving QS-2 (ingestion latency should be dominated by download time, not app overhead) — this design choice is precisely what keeps app overhead low.
6. **Bounded-concurrency (config `+5`) parallel file processing *within* one queue item, but strictly serial *across* items** — INHERITED. A deliberate two-tier concurrency model: parallelize the many small/medium files of one release (fast), but never run two releases concurrently (simple, avoids resource contention across unrelated jobs).
7. **PAR2 descriptor-only parsing, no repair capability** — INHERITED. Likely rationale: repair is unnecessary if you can simply mark a segment "missing" and either skip the file (non-video) or fail the release (video) — cheaper to build than a full Reed-Solomon PAR2 engine, and Usenet providers with good completion rates make missing articles rare enough that "fail and let the Arr re-grab from another indexer/release" is an acceptable substitute for actual repair.
8. **Single shared ingestion code path for SABnzbd-API and WebDAV watch-folder uploads** (`DatabaseStoreCategoryWatchFolder` calling `AddFileController` directly) — INHERITED. Rationale: avoids duplicating queueing/validation logic across two entry points; keeps behavior identical regardless of how an NZB arrives.
9. **Migration gate hard-stop (`BlockUpgradesToV06X`) requiring explicit env-var opt-in for one breaking migration** — INHERITED. Rationale: a genuinely non-backwards-compatible schema change (likely the blob-store migration itself) needed a way to force users to read a warning and back up `/config` before an irreversible upgrade, given there's no automated backup/rollback mechanism in this single-container deployment model.
10. **Prefetch-cache short-circuit ahead of the Usenet stream path** (`BaseStoreStreamFile.TryGetCachedStreamAsync`) — FORK-SPECIFIC (habenspass, episode-prefetch-caching feature). Rationale: for Jellyfin "next episode" prediction, serving a fully-local file avoids Usenet round-trips entirely for the predicted-next episode, directly targeting QS-1/QS-3 for the specific case of sequential episode playback.

## 4. Weak points / risks

- **Serial queue processing caps ingestion throughput at "one release's download+process time" regardless of how much bandwidth/CPU is idle.** Threatens **QS-2** (ingestion latency) whenever a user (or Sonarr's RSS sync) queues several releases at once — the 2nd release doesn't even start downloading until the 1st fully completes (including all post-processing). *(hypothesis)* — suggested experiment: queue 3–4 same-sized releases simultaneously via the API and measure wall-clock time for the last one to reach history, compared to a hypothetical bounded-parallel (e.g., 2-wide) queue processor; also measure whether a single release's per-file concurrency (`GetMaxDownloadConnections()+5`) already saturates the configured provider connection pool, in which case cross-item parallelism would have nothing to gain from provider bandwidth and only value from CPU-bound steps (RAR/7z header parsing, DB writes) overlapping with the next item's download.
- **Blob-store / SQLite dual-consistency risk.** `DavItem.FileBlobId` in SQLite and the corresponding flat file in `CONFIG_PATH/blobs/` are two independent writes (blob file written first, then SQLite row in the same `SaveChangesAsync`, `DavDatabaseContext.cs:613-651`) not covered by a single atomic transaction spanning both storage engines. The code defends against the *"blob write succeeded, SQLite commit failed"* case (catch-and-delete-blob, `DavDatabaseContext.cs:638-650`) but a hard process kill between those two steps, or a `CONFIG_PATH` volume that isn't crash-consistent (e.g., some overlay/network filesystem setups), can produce orphaned blob files. Threatens **QS-8** (crash-safety) at the margins — not filesystem corruption, but silent disk-space leakage until an orphan-cleanup sweep (`RemoveOrphanedFilesSchedulerService`, outside scope) catches it, if it does.
- **No retry cap on `IsRetryableDownloadException()` items.** An item that keeps hitting a "retryable" classification (e.g., persistent partial-provider-outage) will sit in the queue retrying every minute indefinitely, at the front of the priority queue relative to newer items with equal/lower priority (`GetTopQueueItem` orders by `Priority desc, CreatedAt asc` — an old, perpetually-retrying item can effectively head-of-line-block newer same-priority items *if* they're never given a higher priority to jump ahead). Threatens **QS-2/QS-5** — a stuck head-of-queue item delays everything behind it, and there's no automatic time-boxed give-up. *(hypothesis: depends on exactly which exceptions are classified retryable vs not, in `IsRetryableDownloadException()` — that classification lives in `Exceptions/`, outside my scope, so I can't confirm the actual retry-forever surface without reading it.)*
- **Materialized `Path` denormalization has no general rename/move cascade.** `RenameDuplicatesPostProcessor` mutates `Name`+`Path` for the one item it renames but there's no code path in this scope that recomputes descendant paths if a *directory* were renamed/moved (the WebDAV `MoveItemRequest`/`CopyRequest` handlers are in `WebDav/Requests/`, technically in-scope but not read in depth here — worth a follow-up check by whoever documents the `Requests/*` handlers, since a directory move that doesn't cascade `Path` to every descendant would silently desync `Path` from the real `ParentId` chain, breaking anything that trusts `Path` directly — `.strm` generation, rclone-forget). **(needs verification — flagged under Open Questions.)**
- **RAR/7z/PAR2 parsing complexity is a correctness-critical, hand-rolled-adjacent surface.** `RarAggregator.ValidateVolumes`/`ValidatePartNumbers` (`RarAggregator.cs:110-129`) and the whole part-number reconciliation heuristic (header vs. filename, with a "delta" to paper over disagreements) is exactly the kind of logic that's fragile against edge-case release naming conventions in the wild. A bug here doesn't crash the app but can silently produce a corrupted/incomplete playable file (wrong byte ranges) that only surfaces as playback artifacts — no checksum-level validation of the final assembled file against the PAR2 declared hash exists anywhere in this scope. Threatens **QS-1/QS-3** indirectly (bad user experience) and is invisible to **QS-8**'s "never corrupts" guarantee, which really only covers *virtual-filesystem-metadata* corruption, not *content-correctness* of the assembled stream.
- **PAR2 is descriptor-only — no repair.** Any release with missing/damaged articles simply fails (if the affected file is a video) or is silently dropped (if not) — there is no fallback to reconstruct from redundancy the release actually shipped with. Threatens **QS-6**-adjacent expectations (users often equate "PAR2 present" with "some missing articles are recoverable") though this isn't literally one of the 8 listed QS.
- **Full per-path SQLite query chain on every WebDAV path resolution**, no in-memory directory-tree cache in `DatabaseStore`/`DatabaseStoreCollection`. Threatens **QS-3/QS-4** under many concurrent WebDAV clients doing deep-path lookups (e.g., media server library scans) — each `PROPFIND`/`GET` walks N indexed-but-still-real queries for an N-segment path. *(hypothesis)* — suggested experiment: profile SQLite query counts/latency during a Jellyfin full-library scan against the `/content` tree, compare wall-clock with an in-process LRU path→`DavItem` cache in front of `GetDirectoryChildAsync`.
- **`DavItem.NextHealthCheck`/health-check scheduling columns live in this scope's data model, but the health-check *engine* (`HealthCheckService`) is out of scope** — I could not verify whether health-check-triggered re-checks ever intersect with in-flight queue processing (e.g., could a health check and a queue item both touch the same `DavItem` concurrently?). Flagged under Open Questions.

## 5. Alternatives brainstorm

| Alternative | QS-7 (single-container deployability) | QS impact | Migration cost given INHERITED status |
|---|---|---|---|
| **Embedded Postgres** (e.g. via a bundled binary) instead of SQLite | Still dockerizable single-container, but adds a second process to supervise inside the same container (more moving parts, more failure modes for QS-5/QS-8) — net worse for QS-7 | Would help write-concurrency (QS-3 if the serial-queue constraint were ever lifted) but the current serial queue processing means SQLite's single-writer model is *not actually the bottleneck today* | **High** — Database/ is 96%+ inherited; replacing the datastore abandons the ability to pull upstream schema/migration changes entirely. Not worth it unless serial queue processing is *also* being replaced. |
| **LiteDB or a custom flat-file index** instead of SQLite+blob-store hybrid | Comparable single-file deployability to SQLite | Unclear win — the hybrid design already gets "small metadata store + flat-file blobs"; a from-scratch index would need to reinvent transactions/indexing SQLite gives for free | **High**, same reason as above, plus loses EF Core's migration tooling that this repo already leans on heavily (30+ migrations) |
| **Bounded-parallel queue processing (e.g., process up to N items concurrently)** instead of strictly serial | Fully compatible with single-container (just more concurrent connections against the same provider pool) | Directly helps **QS-2** for multi-item ingestion bursts (Sonarr RSS sync queuing several episodes at once); risk to **QS-3/QS-4** if N is set too high relative to configured provider connections/host RAM | **Medium** — `QueueManager.ProcessQueueAsync`'s core loop (`QueueManager.cs:78`) would need reworking, but it's a contained, well-isolated piece; the bigger cost is re-deriving the current careful cancellation/lock semantics (`_semaphore`, `_inProgressQueueItem`) for N-way concurrency instead of 1. Since only ~2 fork commits touch `QueueManager.cs`-adjacent files, this is *comparatively* one of the cheaper "diverge from upstream" options in this domain if the maintainers judge it worth the merge-conflict risk on every future upstream `QueueManager`/`QueueItemProcessor` change. |
| **EF Core → Dapper/raw SQL for the DavItem hot path** (`GetDirectoryChildAsync`, path resolution) | No deployability change | Could reduce per-lookup overhead on the WebDAV path-resolution hot path (QS-3/QS-4), but EF Core's query here is already about as simple as SQL (`WHERE ParentId = ? AND Name = ?` on an indexed pair) — the ORM overhead is likely marginal *(hypothesis, needs a profiler run — none exists in-repo)* | **Medium-High for a full swap, Low for isolated hot paths** — could be done surgically (e.g., only `GetDirectoryChildAsync`) without touching the EF-based aggregation/migration code, limiting merge-conflict blast radius. |
| **Add a lightweight in-process directory/path cache in front of `DatabaseStoreCollection`** | No deployability change | Directly helps QS-3/QS-4 for read-heavy WebDAV traffic (media server scans); needs careful invalidation on the exact same writes that already call `RcloneVfsForget` (a ready-made signal for "these paths changed") | **Low-Medium** — additive, doesn't touch upstream's existing files' logic, just wraps read calls; lowest-risk option on this list for divergence from upstream. |
| **Real PAR2 repair engine** (reconstruct missing segments from recovery slices) instead of descriptor-only parsing | No deployability change | Would improve effective reliability when providers have gaps (adjacent to QS-6, not literally listed) | **High effort regardless of fork status** — this is a from-scratch FEC implementation, not a small diff; upstream-mergeability isn't really the limiting factor here, engineering effort is. |

## 6. Optimization/improvement candidates

1. **Bounded-parallel queue processing (process 2–3 items concurrently instead of 1).** Improves **QS-2** (burst ingestion latency) and **QS-3** indirectly (more overlap between download-bound and CPU-bound phases). Effort: **M**. Risk: **Medium** — touches the queue's cancellation/locking semantics (`QueueManager.cs`) and needs a sane default cap tied to `GetMaxDownloadConnections()` so it doesn't oversubscribe the provider pool; also increases concurrent SQLite writers, though EF+SQLite already handles that today at a smaller scale (health-checks + queue running concurrently).
2. **Add a bounded retry count / exponential-or-capped backoff for `IsRetryableDownloadException()` items**, converting to a hard failure (→ history) after N attempts instead of retrying forever. Improves **QS-2/QS-5** (prevents indefinite head-of-line blocking). Effort: **S**. Risk: **Low** — additive counter field + one comparison in the existing catch block (`QueueItemProcessor.cs:59-75`).
3. **Add a final integrity check comparing the assembled file's actual byte count (and, if cheap, a hash) against the PAR2-declared size/hash before marking the item complete**, instead of relying only on RAR-volume-consistency checks (which don't apply to plain/multipart-mkv files at all). Improves confidence adjacent to QS-1/QS-3 (fewer bad-playback surprises reaching the user). Effort: **M**. Risk: **Low** — read-only verification step, no behavior change on the happy path; needs to decide what to do on mismatch (warn vs. fail) without over-triggering on the known-tolerant 95–100% size-matching heuristic already in `GetFileInfosStep`.
4. **In-process LRU cache for `DatabaseStoreCollection`/`DatabaseStoreCategoryWatchFolder` child lookups**, invalidated on the same write paths that already call `RcloneVfsForget`. Improves **QS-3/QS-4** under concurrent/repeated WebDAV directory traversal (media-server library scans). Effort: **S-M**. Risk: **Low** — purely additive read-path optimization.
5. **Cap or make the SAB-API `PostProcessing` field actually meaningful** (currently accepted and stored but never consulted) — either wire it up to actually skip unpack/repair when the Arr client requests `None`/`Repair`-only, or remove the illusion of configurability. Low urgency, mostly a correctness/expectations cleanup rather than a performance item. Effort: **S**. Risk: **Low**.
6. **Orphaned-blob reconciliation on startup**, scanning `CONFIG_PATH/blobs/` for GUIDs with no matching `DavItem.FileBlobId`/`QueueItem.Id` and deleting them, closing the narrow leak window identified in Weak points. (Note: `RemoveOrphanedFilesSchedulerService` already exists in `backend/Services/` — worth checking, not confirmed in this scope, whether it already covers this exact case before treating it as a gap.) Effort: **S**, pending that check. Risk: **Low**.
