# Usenet Client Stack & Streaming — Research Notes

Scope: `backend/Clients/Usenet/**`, `backend/Streams/**`, `backend/Clients/RadarrSonarr/**`, `backend/Clients/Rclone/**`.
Excludes `Queue/`, `Database/`, `WebDav/*Store*` internals (owned by core-domain agent) except as touchpoints needed to trace the read/seek path.

## 0. Key correction to the brief: the low-level NNTP/yEnc layer is NOT hand-rolled

The brief assumed a "hand-rolled layered NNTP client stack." That's true only for the **upper layers** (pooling, failover, circuit-breaking, prioritization, caching) which do live in this repo. The **raw protocol and yEnc decode** are delegated to two external NuGet packages, both authored by the same upstream org:

- `UsenetSharp` v1.0.6 (`backend/NzbWebDAV.csproj:` `<PackageReference Include="UsenetSharp" Version="1.0.6" />`) — `github.com/nzbdav-dev/UsenetSharp`. Provides `UsenetClient` (raw NNTP connect/auth/STAT/HEAD/BODY/ARTICLE/DATE), `YencStream` (decode), and `AsyncSemaphore`.
- `RapidYencSharp` v1.0.0, a dependency of UsenetSharp — "`.NET bindings for rapidyenc` - a high-performance yEnc encoding/decoding library." This is a P/Invoke binding to the native `rapidyenc` C library (the same SIMD-accelerated (SSE2/AVX2/NEON) decoder used by SABnzbd/NZBGet-adjacent tooling).

**This directly answers one of the brainstorm items below**: SIMD-accelerated yEnc decode is not a future optimization — it's already the status quo via `RapidYencSharp`. `backend/Clients/Usenet/BaseNntpClient.cs:19` wraps `UsenetSharp.Clients.UsenetClient`; `NntpClient`/`INntpClient` in this repo is this project's own abstraction sitting on top.

INHERITED: dependency choice, `BaseNntpClient` wrapper. This matters for §5/§9 framing — don't describe the yEnc decode path as a naive/hand-rolled one.

## 1. Building blocks — the layered client stack

Order of composition (outer wraps inner; each implements `INntpClient`, `backend/Clients/Usenet/INntpClient.cs`):

```
UsenetStreamingClient          (singleton; hot-swaps on config change)
  -> DownloadingNntpClient     (download-concurrency limiting + bandwidth throttling)
    -> MultiProviderNntpClient (failover across configured providers)
      -> MultiConnectionNntpClient  (one per provider; connection-pool + per-command priority)
        -> ConnectionPool<INntpClient>  (bounded pool of...)
          -> BaseNntpClient        (wraps UsenetSharp.UsenetClient — raw protocol)

ArticleCachingNntpClient  — a *separate*, short-lived wrapper used ONLY by the
  Queue ingestion pipeline (see §2b), not by the WebDAV read/seek path.
```

Key files, in order:
- `backend/Clients/Usenet/INntpClient.cs` — interface: core NNTP ops (Connect/Authenticate/Stat/Head/DecodedBody/DecodedArticle/Date) + "optimized for concurrency" exclusive-connection ops + helper ops (`GetYencHeadersAsync`, `GetFileSizeAsync`, `GetFileStream`, `CheckAllSegmentsAsync`).
- `backend/Clients/Usenet/NntpClient.cs` — abstract base with default helper implementations (`GetFileStream` → `NzbFileStream`; `GetFileSizeAsync` → fetches yEnc header of the **last** segment to get `PartOffset + PartSize`).
- `backend/Clients/Usenet/WrappingNntpClient.cs` — delegation base for decorators (`DownloadingNntpClient`, `ArticleCachingNntpClient`, `UsenetStreamingClient` all derive from this); supports hot-swap via `ReplaceUnderlyingClient`.
- `backend/Clients/Usenet/BaseNntpClient.cs` — thin adapter over `UsenetSharp.UsenetClient`; translates failures into this app's exception types and wraps decoded bodies in `YencStream`.
- `backend/Clients/Usenet/MultiConnectionNntpClient.cs:29` — per-provider client. Owns a `ConnectionPool<INntpClient>`, a `ProviderCircuitBreaker`, and does per-command retry-with-new-connection (`RunWithConnection`, line 170) up to `retryCount=1`. Assigns **command-type priority**: STAT/HEAD/DATE → `SemaphorePriority.Low`; BODY/ARTICLE → `SemaphorePriority.High` (lines 61-116) when queueing for a pooled connection.
- `backend/Clients/Usenet/Connections/ConnectionPool.cs` — generic bounded, lazy connection pool (`ConnectionPool<T>`). Explicitly commented `// Note: This class was authored by ChatGPT 3o` (line 18) — see Weak Points. LIFO idle stack, background idle-sweeper (`PeriodicTimer`, half the idle timeout), gate is a `PrioritizedSemaphore`.
- `backend/Clients/Usenet/Connections/ConnectionLock.cs` — RAII wrapper returning/destroying a borrowed connection; also ChatGPT-authored per its doc comment.
- `backend/Clients/Usenet/Connections/ProviderCircuitBreaker.cs` — INHERITED (Anthony Hoivik, PR #400, upstream). 3 consecutive failures trips it; cooldown starts at 60s, doubles to a 5-minute cap on repeated failure, single probe attempt on cooldown expiry.
- `backend/Clients/Usenet/MultiProviderNntpClient.cs` — orders providers by `ProviderType` then descending `AvailableConnections` (line 161-167), filters out tripped-circuit-breaker providers (falls back to "all" if every provider is tripped, so cooldown probes can still fire), and retries the next provider on any exception or on `NoArticleWithThatMessageId` (lines 121-159).
- `backend/Clients/Usenet/DownloadingNntpClient.cs` — wraps the provider-failover client. Separate concern from per-provider connection pooling: a **global download-concurrency semaphore** (`_semaphore`, a second independent `PrioritizedSemaphore`) capped at `usenet.max-download-connections`, plus an optional `TokenBucket` bandwidth limiter. Priority here is resolved not from command type but from an ambient `DownloadPriorityContext` carried on the `CancellationToken` (see §3).
- `backend/Clients/Usenet/UsenetStreamingClient.cs` — the app-wide singleton entry point (constructed once per DI scope/app lifetime), composes everything above from `ConfigManager.GetUsenetProviderConfig()`, and **hot-swaps** the entire underlying stack when `usenet.providers` config changes (`ReplaceUnderlyingClient`, inherited from `WrappingNntpClient`), without needing to restart the app.
- `backend/Clients/Usenet/ArticleCachingNntpClient.cs` — wraps an `INntpClient`, caches decoded article bodies to a temp directory keyed by SHA-256 of the segment ID, de-duplicates concurrent requests for the same segment via a per-segment `SemaphoreSlim`, deletes its whole cache dir on Dispose. **Only instantiated in `backend/Queue/QueueManager.cs:113`** (`using var cachingUsenetClient = new ArticleCachingNntpClient(_usenetClient)`), scoped to one `QueueItem`'s processing lifetime — used during deobfuscation/PAR2/file-processing where the same article may need to be read multiple times. **Not present anywhere in the WebDAV streaming read path.**

### Concurrency primitives (`backend/Clients/Usenet/Concurrency/`)
- `PrioritizedSemaphore.cs` — two FIFO waiter queues (high/low), released via a weighted dice roll (`SemaphorePriorityOdds`, default 100% high) so low-priority waiters aren't fully starved. Used in **two independent places** with different meanings:
  1. Inside `ConnectionPool<T>._gate` — gates raw connection acquisition, priority = command type (BODY/ARTICLE high, STAT/HEAD/DATE low).
  2. Inside `DownloadingNntpClient._semaphore` — gates the *download-concurrency* budget, priority = interactive-vs-background as set by `DownloadPriorityContext`.
- `SemaphorePriority` (High/Low), `SemaphorePriorityOdds` (configurable split, exposed as "streaming-priority"/"bandwidth-streaming-reserve" config).
- `Throttling/TokenBucket.cs` + `ThrottledYencStream.cs` — FORK-SPECIFIC (`habenspass`). Async token bucket (1-second burst cap), same odds-based dice-roll priority split as `PrioritizedSemaphore` when both interactive and background traffic are bandwidth-constrained simultaneously. Wraps `YencStream` so every byte actually read (not the advertised article size) is metered.
- `Statistics/ProviderCountingYencStream.cs` + `ProviderUsageStatsAggregator.cs` — FORK-SPECIFIC (authored by "Claude" per git log, part of the `habenspass` "Add per-provider Usenet usage statistics" PR, commit `7ac1433`). Same wrapper-stream pattern as throttling, counts bytes per provider for the UI.

### Ambient priority propagation (`backend/Clients/Usenet/Contexts/`) — INHERITED
Because `DownloadingNntpClient` sits below `MultiProviderNntpClient`/`MultiConnectionNntpClient` and has no visibility into *why* a read is happening (interactive stream vs. background queue download), the code attaches a small ambient context keyed by `CancellationToken` identity:
- `CancellationTokenContext.cs` — a static `ConcurrentDictionary<(CancellationToken, Type), object?>` used as a poor-man's per-operation "ambient" store (there's no `AsyncLocal` flow here because the token, not the async-call-stack, is the correlation key — necessary because a `MultiSegmentStream`'s background download loop runs on its own detached `Task`, outside the original call's async-local scope).
- `ContextualCancellationTokenSource.cs` — when a linked `CancellationTokenSource` is created (e.g. `MultiSegmentStream:43`), it copies forward any `DownloadPriorityContext` already attached to the parent token(s), so priority survives the "spawn a detached background download loop per multi-segment read" pattern.
- `DownloadPriorityContext.cs` — just wraps a `SemaphorePriority`.
- **Where it's set**: `backend/WebDav/Base/BaseStoreStreamFile.cs:22-23` — every WebDAV `GetReadableStreamAsync` call explicitly sets `SemaphorePriority.High` on the request's `CancellationToken` before descending into `GetStreamAsync`, and disposes the context on `HttpContext.Response.OnCompleted`. Background queue downloads (`QueueItemProcessor`/`QueueManager`) never set this, so `DownloadingNntpClient.ResolvePriority` (line 82-86) defaults them to `SemaphorePriority.Low`. **This is the concrete mechanism behind QS-3's "streaming reads shouldn't stall behind queue downloads."**

## 2. Key runtime interactions

### 2a. Fresh sequential read/stream start (no seek)
1. WebDAV `GET` with no `Range` header hits `GetAndHeadHandlerPatch.HandleRequestAsync` (`backend/WebDav/Base/GetAndHeadHandlerPatch.cs:89`), which calls `entry.GetReadableStreamAsync`.
2. `BaseStoreStreamFile.GetReadableStreamAsync` (`backend/WebDav/Base/BaseStoreStreamFile.cs:16`) first checks a **local prefetch cache** (`TryGetCachedStreamAsync`, FORK-SPECIFIC, part of the Jellyfin-webhook predictive-prefetch feature — owned by core-domain, noted here only as a bypass of the entire NNTP stack when a complete cached copy already exists on disk).
3. On a cache miss, sets `DownloadPriorityContext{High}` on the token, then calls the subtype-specific `GetStreamAsync` → `DavFileStreamFactory.GetStreamAsync` (`backend/WebDav/DavFileStreamFactory.cs:15`), which switches on `DavItem.SubType`:
   - `NzbFile` → `usenetClient.GetFileStream(segmentIds, fileSize, articleBufferSize)` → `NzbFileStream` (`backend/Streams/NzbFileStream.cs`).
   - `RarFile`/`MultipartFile` → `DavMultipartFileStream` (concatenates per-file-part `NzbFileStream`s via `CombinedStream`), optionally wrapped in `AesDecoderStream` if the archive is password-protected.
4. First `ReadAsync` on `NzbFileStream` (position 0) lazily creates the inner stream: `GetFileStream(0, ct)` → since `rangeStart == 0`, skips the interpolation search and goes straight to `GetMultiSegmentStream(0, ct)` → `MultiSegmentStream.Create` (`backend/Streams/MultiSegmentStream.cs:19`).
5. `MultiSegmentStream`'s constructor immediately spawns a **detached background pipeline task** (`DownloadSegments`, line 47) that, for each segment in order: acquires an *exclusive connection* (`AcquireExclusiveConnectionAsync` — this is what actually waits on `DownloadingNntpClient._semaphore` with High priority, then on the per-provider `ConnectionPool` gate with High priority since it's a BODY command), issues `DecodedBodyAsync`, and pushes the resulting `Task<Stream>` onto a **bounded channel** (capacity = `articleBufferSize`) — i.e. it read-aheads/prefetches up to N segments' bodies concurrently with the consumer.
6. The consumer's `ReadAsync` pulls the next `Task<Stream>` off the channel, awaits it (may already be complete if the read-ahead won the race), and streams bytes out.
7. Under the hood, `DecodedBodyAsync` traverses the full stack: `DownloadingNntpClient` (acquire slot, wrap in `ThrottledYencStream` if bandwidth-limited) → `MultiProviderNntpClient` (pick healthiest/most-available provider) → `MultiConnectionNntpClient` (acquire pooled connection, issue BODY, wrap in `ProviderCountingYencStream`) → `ConnectionPool` (reuse idle connection or open a **new TCP+TLS connection and re-authenticate** if none idle) → `BaseNntpClient`/`UsenetSharp` (raw NNTP BODY + yEnc decode via RapidYencSharp).
8. First byte reaches the client after: connection acquisition (0 if idle connection available, else full TCP+SSL handshake + NNTP AUTHINFO round-trip) + one BODY command round-trip + yEnc decode of however many bytes are needed to fill the read buffer.

### 2b. Mid-playback seek to an arbitrary offset — this is the QS-1 critical path
1. Client (e.g. a video player scrubbing) issues a WebDAV `GET` with a `Range: bytes=X-` header. `GetAndHeadHandlerPatch.CopyToAsync` (`backend/WebDav/Base/GetAndHeadHandlerPatch.cs:164`) calls `src.Seek(start, SeekOrigin.Begin)` on the stream **before any read**, per the "prefer seeking instead of draining data" comment (line 169).
2. `NzbFileStream.Seek` (`backend/Streams/NzbFileStream.cs:43`) is cheap/synchronous: just records `_position`, disposes any existing inner stream, returns. No network I/O happens yet — it's deferred to the first `ReadAsync`.
3. First `ReadAsync` calls `GetFileStream(_position, ct)` (line 70). Since `_position != 0`, it calls `SeekSegment` (line 55), which runs `InterpolationSearch.Find` (`backend/Utils/InterpolationSearch.cs`) over the segment index space, using **linear interpolation** (assumes roughly uniform per-segment byte size, true for yEnc-encoded NZB parts except the last) to guess which segment index contains the target byte, converging in **very few probes** (typically 1-3 for uniformly-sized parts) rather than `O(log n)` binary-search probes.
4. **Each probe is a full round trip**: `usenetClient.GetYencHeadersAsync(segmentId, ct)` (`NntpClient.cs:76`) → `DecodedBodyAsync` (full BODY command, full connection-acquisition/priority/pool path from §2a step 7) → reads only as many bytes as needed to parse the yEnc header line, then the stream is disposed. **Because there is no `ArticleCachingNntpClient` in this path**, every probe is a live, uncached NNTP command — a seek that requires 2 interpolation probes pays for 2 full connection-acquisition-plus-BODY-command round trips before the "real" data segment is even fetched.
5. Once the containing segment is found, `GetMultiSegmentStream(foundIndex, ct)` creates a fresh `MultiSegmentStream` starting at that segment (which itself immediately issues its own exclusive-connection-acquisition + BODY command for the *first* segment it will actually stream), then `DiscardBytesAsync` throws away the leading bytes within that segment up to the exact requested offset (i.e., the segment is still fetched and decoded in full up to the offset — no support for skipping to a mid-article byte offset over the wire).
6. **Total cost of a cold seek** ≈ (N interpolation probes × 1 connection-acquire + 1 BODY round trip each, probes largely serialized because each depends on the previous one's result) + (1 more connection-acquire + BODY round trip for the actual target segment) + (decode/discard of leading bytes in that segment). Compare to §2a's fresh start, which pays exactly one connection-acquire + BODY round trip (segment 0) before first byte. **A seek is strictly slower than a fresh start by roughly the interpolation-probe count**, and every probe can additionally queue behind the `DownloadingNntpClient` semaphore and connection-pool gate if other streams/queue downloads are contending — though probes get `SemaphorePriority.High` same as the real read, so they queue ahead of background queue downloads, just not ahead of each other or other concurrent interactive streams.
7. For `RarFile`/`MultipartFile` subtypes, `DavMultipartFileStream.Seek` (`backend/Streams/DavMultipartFileStream.cs:37`) does an additional **in-memory, no-network** linear scan (`SeekFilePart`, line 71) over file-part boundaries first, then delegates into the same per-part `NzbFileStream`/interpolation-search mechanism for the byte offset within that part.

## 3. Architectural decisions

| Decision | Tag | Notes |
|---|---|---|
| Raw NNTP protocol + yEnc decode delegated to `UsenetSharp`/`RapidYencSharp` (external, same-org, native SIMD decoder) | INHERITED | See §0. Not hand-rolled at the lowest level. |
| Hand-rolled layering above that (pool, failover, circuit-breaker, priority, bandwidth) instead of e.g. wrapping everything in one monolithic client | INHERITED (structure) | Each concern (pooling, failover, priority, caching) is a separate decorator implementing the same `INntpClient` interface — easy to test/compose in isolation, but means every new cross-cutting concern (throttling, stats) adds another decorator layer and another place priority/cancellation must be threaded through correctly. |
| Per-provider `MultiConnectionNntpClient` + `ConnectionPool<INntpClient>`, one pool per configured provider | INHERITED | Enables independent max-connections per provider (a real Usenet-provider constraint) and independent circuit-breaking. |
| `ArticleCachingNntpClient` scoped per-`QueueItem`, disk-backed, deleted on dispose | INHERITED | Only used by ingestion (dedup repeated PAR2/deobfuscation reads of the same article), explicitly NOT used by the streaming read path — the streaming path re-fetches identical segments from Usenet on every seek/re-read with zero caching (see Weak Points). |
| `PrioritizedSemaphore` (two-queue, odds-based dice roll) instead of separate connection pools per priority class or OS-level QoS | INHERITED (connection-pool gate use); FORK-SPECIFIC (its reuse in `DownloadingNntpClient` for interactive-vs-background, and in `TokenBucket` for bandwidth) | A single-container deployment can't rely on OS-level network QoS across NNTP TCP connections easily without root/NET_ADMIN, so an in-process, config-tunable priority scheme is the pragmatic choice. Odds-based (not strict priority) avoids starving background queue downloads entirely. |
| `CancellationToken`-keyed static ambient context (`CancellationTokenContext`) to flow "is this an interactive read" across a detached background download task | INHERITED | Unusual pattern (would more idiomatically be `AsyncLocal<T>`, but `AsyncLocal` wouldn't survive `Task.Run`-detached continuations the way this needs to); works but is a global mutable dictionary keyed on token identity — see Weak Points for lifecycle risk. |
| Bandwidth throttling (`TokenBucket`) and per-provider usage stats (`ProviderCountingYencStream`) added as additional stream decorators | FORK-SPECIFIC | Both follow the exact same "wrap `YencStream`, override `ReadAsync`" pattern already established by `CachedYencStream` — good consistency, low risk of introducing a new composition style. |
| Custom `Stream` composition per request (`SubStream`/`LimitedLengthStream`/`CombinedStream`/`ProbingStream`/`MultiSegmentStream`) instead of one monolithic stream class | INHERITED | Lets RAR/multipart/AES/plain-file cases share the same segment-fetching primitives (`NzbFileStream`, `MultiSegmentStream`) while composing only the transform each case needs. |
| Fully async all the way down on the WebDAV hot path | INHERITED | Verified: no `.Result`/`.Wait()` blocking calls found in `Clients/Usenet` or `Streams` on the read path (the one `task.Result` hit in `NntpClient.cs:130` is a tuple field access, not `Task.Result`). Sync `Stream.Read` overloads (`AesDecoderStream`, `DavMultipartFileStream`, `MultipartFileStream`, `CancellableStream`) shim to `ReadAsync(...).GetAwaiter().GetResult()` but these are compatibility fallbacks, not exercised by `GetAndHeadHandlerPatch` (which calls `ReadAsync` exclusively). |
| `UsenetStreamingClient` hot-swaps its entire underlying stack on `usenet.providers` config change, in place, without restarting the app | INHERITED | Nice operationally for a single long-running container; relies on old in-flight streams keeping their reference to the pre-swap client (they hold `INntpClient` references acquired before the swap) while new requests get the new stack. |

## 4. Weak points / risks

- **QS-1**: Every mid-playback seek pays for 1+ extra live NNTP round trips (interpolation-search header probes) with **zero caching**, because `ArticleCachingNntpClient` is not used on the streaming path (`backend/Queue/QueueManager.cs:113` is its only call site). A player that seeks frequently (scrubbing) will repeatedly re-fetch and re-decode the *same* boundary segments' headers. (hypothesis: the actual added latency per seek is small — likely 1-3 probes, each one connection-acquire + BODY round trip, so tens to low-hundreds of ms on a healthy provider — but this is unverified.) **Confirming experiment**: instrument `SeekSegment`/`GetYencHeadersAsync` call counts and wall-clock time under a mocked or real NNTP server, seeking to N random offsets in a large multi-part file, and compare first-byte latency to a cold sequential start.
- **QS-1/QS-3**: Worst case for both a fresh start and a seek is when the connection pool has no idle connections and a brand-new TCP+SSL connection plus NNTP `AUTHINFO` must be established synchronously in the request path (`ConnectionPool.GetConnectionLockAsync`, `backend/Clients/Usenet/Connections/ConnectionPool.cs:107-120`) — there is no pre-warming of idle connections; the pool is purely on-demand/lazy. On a homelab host, if all `maxConnections` slots are already in use by other streams/queue downloads, a new stream request queues behind them (a High-priority queue, so it queues only behind other High-priority waiters, but if the provider's max-connections is fully saturated by other *interactive* streams, a 3rd/4th concurrent stream will wait for one to free up). (hypothesis) **Confirming experiment**: with `maxConnections` set low (e.g. 2) and a mocked NNTP server with an artificial connect+auth delay, start 3-4 concurrent streams and measure per-stream first-byte latency for streams 3 and 4.
- **QS-4 (hypothesis)**: Per-article/per-segment buffer allocations (`CachedYencStream`'s `FileStream` buffers at `bufferSize: 81920`, `ArticleCachingNntpClient.cs:234/242/258`; `MultiSegmentStream`'s bounded channel holding up to `articleBufferSize` in-flight `Task<Stream>`; `AesDecoderStream`'s fixed 4KB plaintext + 128-byte ciphertext buffers) haven't been profiled for GC pressure under several concurrent 20GB-file streams. **Confirming experiment**: `dotnet-counters`/`dotnet-trace` a container running 2-4 concurrent streams over an extended period, watching Gen0/Gen1 collection frequency and LOH allocations.
- **Two independently-configured priority mechanisms that don't compose transparently**: command-type priority in `ConnectionPool`'s gate (BODY/ARTICLE always High regardless of caller) vs. context-based priority in `DownloadingNntpClient`'s semaphore (interactive vs. background, defaulting to Low if unset). A background queue download's BODY/ARTICLE command still gets High priority *at the per-provider connection-pool gate* even though it's Low priority *at the download-concurrency semaphore* one layer up — meaning queue downloads that do get a download-concurrency slot then compete equally with interactive reads for the underlying connection. This is subtle enough to misconfigure/regress without anyone noticing (no tests exist for either).
- **`ConnectionPool.cs` and `ConnectionLock.cs` are explicitly documented as ChatGPT-authored** (`backend/Clients/Usenet/Connections/ConnectionPool.cs:18`, `ConnectionLock.cs:7`) with no accompanying unit tests in the repo (there is no backend test project at all, per CLAUDE.md). This is the connection-lifecycle code every single stream and queue download depends on — worth flagging as a review/test-coverage gap regardless of code quality, since AI-generated concurrency code is exactly the kind of thing that benefits most from targeted tests (lock/release races, idle-sweeper vs. concurrent borrow, disposal races).
- **`CancellationTokenContext`'s static dictionary** (`backend/Clients/Usenet/Contexts/CancellationTokenContext.cs:7`) is keyed by `(CancellationToken, Type)` and relies on every caller disposing the returned `CancellationTokenContext` handle to remove the entry (`BaseStoreStreamFile.cs` does this via `Response.OnCompleted`). If any future call site sets context and fails to dispose (e.g. an exception path that skips the `OnCompleted` registration, or a cancellation token that's cached/reused unexpectedly), entries leak for the process lifetime — slow, unbounded growth (hypothesis, unverified — no repro attempted).
- **QS-6**: Circuit breaker (`ProviderCircuitBreaker`) trips after 3 *consecutive* failures per provider and cools down starting at 60s, doubling to a 5-minute cap. Tuning is static/hardcoded (`FailureThreshold = 3`, `InitialCooldown = 60s`, `MaxCooldown = 5min`, `ProviderCircuitBreaker.cs:18-20`), not configurable. A provider with intermittent (non-consecutive) failures never trips; a provider that's merely slow (not failing) never trips either — circuit-breaking here is purely failure-count-based, not latency-based, so a "zombie" slow-but-technically-successful provider could still degrade QS-1/QS-3 without ever failing over. (hypothesis)
- **No read-ahead/prefetch tuning guidance**: `articleBufferSize` (the `MultiSegmentStream` channel bound / read-ahead depth) is threaded through as a plain `int` parameter from `DavFileStreamFactory` down; its actual configured value and how it's chosen wasn't traced in this pass (it's constructed at call sites outside this scope — likely `ConfigManager`, owned by core-domain/config). Flagging as an open question for synthesis.

## 5. Alternatives brainstorm

| Alternative | QS improved / hurt | Effort | Migration cost if replacing INHERITED code | Notes |
|---|---|---|---|---|
| Pre-warm/keep N idle connections ready per provider instead of pure on-demand `ConnectionPool` | QS-1, QS-3 (faster cold start) | S-M | Low — `ConnectionPool<T>` already supports a factory + idle cache; adding a background "keep-warm" loop that opens connections up to a floor is additive, not a rewrite. | Directly targets the worst-case "new TCP+SSL+AUTHINFO synchronously in the request path" scenario. Cost: idle connections consume a provider connection slot even when unused, and providers often bill/limit by concurrent connections — needs to be user-configurable, not a fixed default. |
| Cache yEnc headers (not full articles) for the segment-index seek path, independent of `ArticleCachingNntpClient`'s full-article disk cache | QS-1 | S | Low — `NzbFileStream`/`InterpolationSearch` already isolate `GetYencHeadersAsync` as the exact thing being probed; an in-memory `ConcurrentDictionary<segmentId, UsenetYencHeader>` scoped to the `NzbFileStream`'s lifetime (or shared per-DavItem across requests) would let repeat seeks into the same file skip re-probing already-visited segments, without the full disk-caching machinery `ArticleCachingNntpClient` uses for ingestion. | Cheapest, most targeted fix for QS-1's repeated-seek case; much smaller than adopting `ArticleCachingNntpClient` on the streaming path (which would also cache full bodies, wasted for pure seeks). |
| Replace linear/dictionary-based `CancellationTokenContext` ambient-context with a purpose-built parameter threaded explicitly through `INntpClient` calls | QS-4 (rules out a leak risk), code clarity | M | Medium — every `INntpClient` method signature in the interface and all 6+ implementations would need a `SemaphorePriority` parameter, or the calls that currently rely on ambient context (`MultiSegmentStream`'s detached background task) would need restructuring. | Not urgent unless the leak hypothesis above is confirmed; current approach works, just fragile. |
| Replace hand-rolled `ConnectionPool`/`ConnectionLock` with a review pass + targeted unit tests (not a rewrite) | QS-3, QS-4, general risk | S (tests) / M (any fixes found) | N/A — additive | Given the explicit "authored by ChatGPT" comment and zero test coverage, the highest-leverage move is verifying this code under concurrent load/disposal races before optimizing anything else in this subsystem. |
| Replace the hand-rolled stack with an existing full-featured .NET Usenet client library | — | — | — | No existing full-stack alternative was found (searched only within local knowledge, not live web) that provides connection pooling + multi-provider failover + circuit breaking + yEnc decode as one package for .NET; `UsenetSharp` (already in use) appears to be this project's own foundational library, so "replace with an external library" isn't really on the table — the realistic alternative space is entirely about the decorator layers built on top of it, not the raw client. |

## 6. Optimization / improvement candidates

1. **Cache yEnc headers per NzbFileStream/DavItem to avoid repeat interpolation-search probes on repeated seeks.** QS improved: QS-1. Effort: S. Risk: Low (pure addition, no behavior change to the happy path).
2. **Add an optional idle-connection floor (keep-warm) per provider, configurable, defaulting to 0 (today's behavior) so it's opt-in for users who want faster cold seeks at the cost of holding provider connection slots.** QS improved: QS-1, QS-3. Effort: S-M. Risk: Low-Medium (must respect provider max-connections and not fight the existing idle-sweeper).
3. **Add unit tests for `ConnectionPool<T>`/`ConnectionLock<T>` covering concurrent acquire/return/replace/dispose races**, given the explicit "AI-authored, no tests" status of code every stream and queue download depends on. QS improved: QS-3, QS-4, QS-8 (crash-safety of connection lifecycle). Effort: S-M. Risk: Low (test-only change, may surface latent bugs to then fix).
4. **Add latency-aware signal to `ProviderCircuitBreaker`** (e.g., trip on sustained high command latency, not just consecutive hard failures). QS improved: QS-1, QS-3, QS-6. Effort: M. ## OPEN QUESTIONS FOR SYNTHESIS

- **`articleBufferSize`'s actual value/config surface** wasn't traced — it's passed into `DavFileStreamFactory.GetStreamAsync` and `NntpClient.GetFileStream` from call sites in `WebDav/` (core-domain's territory). Synthesis needs core-domain's input on where/how this is configured and its default, to complete the QS-3/QS-4 tradeoff picture.
- **The predictive episode-prefetch cache** (`BaseStoreStreamFile.TryGetCachedStreamAsync`, FORK-SPECIFIC, Jellyfin webhook-driven) entirely bypasses this subsystem when a hit occurs — core-domain owns that feature's design, but it materially changes the *actual* frequency with which QS-1's cold-seek path is even exercised in practice (a well-tuned prefetch cache could make seek latency moot for the common "next episode" case, while doing nothing for true random-scrub seeks). Worth cross-referencing in the synthesized quality-scenario analysis.
- **Provider config surface** (`UsenetProviderConfig`, `ConfigManager.GetUsenetProviderConfig()/GetMaxDownloadConnections()/GetStreamingPriority()/GetBandwidthLimitMbps()`) lives outside this scope (likely `Config/`, not assigned to any agent's explicit scope per the brief) — whoever owns crosscutting concerns (§8) should confirm these are documented/discoverable for an operator tuning a homelab deployment.
- **Exact behavior of `UsenetSharp.YencStream.Dispose()` when a consumer reads only the yEnc header and abandons the rest of a BODY response** (as `GetYencHeadersAsync` does on every interpolation-search probe) is unverified — whether the underlying connection is left in a valid state for reuse (fully drained) or is forced into replacement (extra reconnect cost per seek probe) depends on internals of the external `UsenetSharp` package not inspected in this pass (decompiling/sourcing that package was out of scope). This materially affects the true cost model in §2b step 4 and would sharpen the QS-1 hypothesis significantly if resolved.
