# Frontend Architecture — Research Notes

Scope: `frontend/app/**`, `frontend/server.ts`, `frontend/server/**`, `frontend/app/clients/backend-client.server.ts`, `frontend/package.json`, `frontend/vite.config.ts`. Backend internals are out of scope except as call targets.

## 1. Building blocks

### Filesystem routing
- `frontend/app/routes.ts:1-9` — routes are discovered via `@react-router/fs-routes`'s `flatRoutes()` over `app/routes/*`, plus one manually-registered catch-all: `{ path: "/explore/*", file: "routes/explore/route.tsx" }`. The manual entry exists because `/explore` needs to match arbitrary nested WebDAV paths, which fs-routes' file-name convention can't express directly.
- Route inventory (dirs under `frontend/app/routes/`): `_index` (dashboard/nav shell), `login`, `logout`, `onboarding`, `queue` (SABnzbd-style queue/history UI), `health` (health-check queue/history), `settings` (+ subroutes: `arrs`, `cache`, `library`, `maintenance/*`, `rclone`, `repairs`, `sabnzbd`, `usenet`, `webdav`), `settings.update`, `explore` (WebDAV file browser).
- Each route folder typically co-locates `route.tsx` with `components/` and sometimes `controllers/` (e.g. `routes/queue/controllers/websocket-controller.ts`).

### The hand-rolled Express server
Two layers:
1. `frontend/server.ts:1-95` — the process entry point. Sets up `compression` (with a path-based `filter`, see below), disables `x-powered-by`, and branches on `NODE_ENV`: development uses Vite middleware mode + `ssrLoadModule("./server/app.ts")` per request; production serves `build/client` as static assets, uses `morgan("tiny")` request logging (skipping <400 and favicon), and imports the built server module. Both branches wrap the same `express()` app in a raw `http.createServer` so a single `ws.WebSocketServer` can attach to the same port (`server.ts:88-90`).
2. `frontend/server/app.ts:1-81` — the actual request pipeline, run identically in dev and prod via the SSR-loaded/imported module. Order:
   - `forwardToBackend` (`http-proxy-middleware`, `app.ts:19-31`) proxies to `process.env.BACKEND_URL` for any request whose method is `PROPFIND`/`OPTIONS`, or whose path starts with `/api`, `/view`, `/.ids`, `/nzbs`, `/content`, `/completed-symlinks` (`app.ts:52-65`). For `/api/*` requests from an authenticated browser session that don't already carry an API key, `setApiKeyForAuthenticatedRequests` (`app.ts:33-48`) injects `x-api-key: $FRONTEND_BACKEND_API_KEY` — this is how the shared frontend/backend trust boundary described in CLAUDE.md is actually enforced at the edge.
   - `authMiddleware` (`app.ts:69`) — gates everything **not** matched above.
   - `createRequestHandler` from `@react-router/express` (`app.ts:72-81`) — hands off to React Router SSR for everything else.
3. `frontend/server/websocket.server.ts:1-120` — a relay, not a data source. On the browser side, `wss.on("connection")` (line 13) requires `isAuthenticated(request)` (session cookie) before accepting a subscription; clients send a JSON topic map, and the server tracks per-topic subscriber sets plus a `lastMessage` cache used to replay current state to newly-subscribed clients (`state` topic mode, lines 30-33). On the backend side, `initializeWebsocketClient` (line 59) is a single persistent outbound WS connection from the Node process to the backend's `/ws` endpoint, authenticated once at connect via `FRONTEND_BACKEND_API_KEY` (line 78), with reconnect/backoff (lines 101-108). Backend messages are tagged `{Topic, Message}` and fanned out to subscribed browser sockets (lines 81-93).

### `backend-client.server.ts` as the access layer
`frontend/app/clients/backend-client.server.ts` — a single `BackendClient` class, one method per backend endpoint (`isOnboarding`, `createAccount`, `authenticate`, `getQueue`, `getHistory`, `addNzb`, `listWebdavDirectory`, `getConfig`, `updateConfig`, `getHealthCheckQueue`, `getHealthCheckHistory`, `getProviderUsageStats` — lines 2-243). Every call is a raw `fetch` against `$BACKEND_URL/api/*` with `x-api-key: $FRONTEND_BACKEND_API_KEY` attached manually per-call (e.g. lines 9, 27, 49, 73...). This is server-only code (`.server.ts` suffix + React Router convention strips it from the client bundle) — it's the loader/action-side counterpart to the Express proxy: proxy handles pass-through/streaming paths, this client handles typed request/response JSON calls made from route loaders/actions.

### Why compression is disabled for proxied/streamed paths
`server.ts:14-32` — the `compression` middleware's `filter` explicitly excludes `/view`, `/.ids`, `/nzbs`, `/content`, `/completed-symlinks`, and `/api`. The inline comment (`server.ts:16`) states the reason: compressing these responses would strip/rewrite `Content-Length`, breaking HTTP range requests used for seeking. `git log` (`c37be6f`, nzbdav-dev, 2026-03-08, "Fixed bug surfaced by rclone v1.73.2; support proxying url-encoded requests") shows this was tightened in response to a real regression, not a preemptive design choice — the original was a blanket `app.use(compression())` (pre-`12be368`).

## 2. Key runtime interactions

### Browser range/seek request path
`explore/route.tsx:63-69` builds file links as plain `<a href="/view/{relativePath}?downloadKey={hash}&extension={ext}">` — not a React Router `<Link>`. This matters: clicking/loading a file (or a `<video>`/external player hitting that URL) is a **normal browser HTTP request**, not an SSR navigation. It never touches a React Router loader or the SSR render path at all. Its path through the server is:
1. `server.ts` → `compression` middleware skips it (path starts with `/view`) → passed through uncompressed, `Content-Length` intact.
2. `server/app.ts:56` matches `path.startsWith("/view")` → `setApiKeyForAuthenticatedRequests` is a no-op (only acts on `/api`) → `forwardToBackend(req, res, next)` proxies directly to `$BACKEND_URL`, `changeOrigin: true`.
3. Because this branch returns before reaching `authMiddleware` (`app.ts:69`), **session-cookie auth is not checked here at all** for `/view` (or `/.ids`, `/nzbs`, `/content`, `/completed-symlinks`) requests. Instead, authorization is a capability token: `getDownloadKey(path)` (`frontend/app/auth/downloads.server.ts:3-6`) computes `sha256(path + FRONTEND_BACKEND_API_KEY)` server-side when the directory listing is rendered, embeds it as `?downloadKey=`, and (per the paired `verifyDownloadKey` in the same file) something on the backend must validate it per-request. This design lets external players (mpv/VLC/Kodi/`*.strm` files consumed by Jellyfin) stream without a browser session cookie.
4. The proxy's only added logic on the response side is `proxyRes.on('close', ...)` (`app.ts:23-29`), a hygiene fix ensuring `res.end()` fires if the client socket closes before the backend response naturally ends — not a buffering point.

So for QS-1 (seek latency), the frontend Express process is a thin, non-buffering passthrough for the actual byte stream once compression is excluded and auth is bypassed via the capability token; the meaningful proxy-layer costs are one extra TCP hop + `http-proxy-middleware`'s per-chunk relay, not SSR or compression.

### Login/session flow
- `frontend/app/auth/authentication.server.ts` — `createCookieSessionStorage` (`__session` cookie, `httpOnly`, `sameSite: strict`, `secure` gated on `$SECURE_COOKIES`, 1-year `maxAge`, signed with `$SESSION_KEY` or a random secret generated at boot if unset — line 19). `isAuthenticated` (line 25) reads the cookie from either a `Request` (SSR/loader context) or raw `IncomingMessage` (websocket upgrade context) — the dual-input signature is precisely what lets the same auth check gate both React Router routes and websocket connections. `IS_FRONTEND_AUTH_DISABLED` (line 6, `$DISABLE_FRONTEND_AUTH`) is an escape hatch that short-circuits all checks to `true`.
- `login()` (line 39) calls `backendClient.authenticate` (delegates real credential check to the .NET backend) then stores `{username}` in the session; `logout()` (line 46) unsets it.
- `auth-middleware.server.ts:5-27` — an explicit allowlist (`PUBLIC_PATHS`: `/__manifest`, `/login`, `/login.data`, `/onboarding`, `/onboarding.data`) is checked first; everything else requires `isAuthenticated`, else a 302 to `/login`. Note this middleware only runs for requests that fall through the proxy branch in `app.ts` (i.e., real SSR page routes) — the streamed/API paths are gated separately as described above.

## 3. Architectural decisions

| Decision | Tag | Notes |
|---|---|---|

Original authors chose SSR; nothing about the app's data (queue/health tables, settings forms) *requires* server rendering — these are behind auth and not indexed/crawled. |
| Hand-rolled Express server (vs. stock `@react-router/serve`, vs. proxy in front via Caddy/nginx/Traefik) | INHERITED | Predates the fork; `server.ts`/`server/app.ts` exist specifically to host the WebDAV/API proxy, websocket relay, and custom compression filter in the same process as SSR — none of which the stock React Router server provides out of the box. |
| Session-based cookie auth (vs. token-based) for the browser UI, with a separate sha256 capability-token scheme for streamed media links | INHERITED | `authentication.server.ts` (session) + `downloads.server.ts` (per-path token). Two distinct auth mechanisms coexist because streaming clients (external players) can't participate in cookie-based session auth. |
| API key injection happens in the frontend proxy layer, not per-loader | INHERITED | `setApiKeyForAuthenticatedRequests` (`app.ts:33-48`) is centralized so any authenticated browser session automatically gets backend API access without every route needing to know about `FRONTEND_BACKEND_API_KEY` — but `backend-client.server.ts` calls still attach the key manually per-call for *loader-initiated* fetches (which are server-to-server, not proxied browser requests), so the key-attachment logic is actually duplicated across two code paths (see weak points). |
| Real-time queue/history/connection-count via a single relayed WebSocket rather than polling | INHERITED | `git log` on `live-usenet-connections.tsx` shows iterative feature history ("Added real-time queue/history", "Added support for multiple providers", "Display live usenet connection count") — an evolved, not day-one, design. |
| `http-proxy-middleware`'s `http-proxy` dependency overridden to `http-proxy-node16` | INHERITED | `frontend/package.json` `overrides` block — a compatibility shim, not a chosen architecture, but signals the proxy library needed patching to work on the Node version in use. |
| Fork-specific frontend work is exclusively feature/settings UI, not architecture | FORK-SPECIFIC | `git log --author=habenspass -- frontend/` shows only: predictive episode-prefetch (Jellyfin webhook) settings UI, bandwidth-limit split UI, sample-file rejection/cleanup UI. None touch `server.ts`, `server/app.ts`, `websocket.server.ts`, `auth-middleware.server.ts`, or `routes.ts`. The fork has not altered frontend architecture at all so far. |

## 4. Weak points / risks

- **Proxy route list duplicated in two places and must stay in sync with backend routing.** The exact same set of path prefixes (`/api`, `/view`, `/.ids`, `/nzbs`, `/content`, `/completed-symlinks`) is hand-maintained independently in `server.ts:19-26` (compression filter) and `server/app.ts:52-61` (proxy/auth-bypass routing). A new backend-exposed path that needs proxying requires editing both files correctly; missing one produces either a compressed range response (breaks seeking, QS-1) or an unauthenticated page falling through to SSR 404 instead of reaching the backend. No test guards this.
- **Two long-lived Node/.NET processes on one homelab host, with the Node process doing both SSR rendering and byte-streaming proxying in a single event loop.** Under concurrent load (someone browsing `/queue` or `/settings` while 2-4 streams are active — QS-3/QS-4), CPU-bound SSR render work and the proxy's per-chunk stream relaying share the same Node main thread. Node's I/O-bound proxying itself is cheap (event-loop friendly), but any synchronous SSR render work (component tree serialization) could introduce jitter in in-flight stream relaying. **(hypothesis)** — no profiling exists; a concrete experiment would be to hammer `/settings` page loads via `ab`/`wrk` while measuring time-to-first-byte on a concurrent `/view/*` range request.
- **`/view`, `/.ids`, `/nzbs`, `/content`, `/completed-symlinks` requests skip `authMiddleware` entirely** (`app.ts:52-65` returns before line 69) and rely solely on the sha256 `downloadKey` capability token embedded in URLs generated by `explore/route.tsx`. Because the token is a deterministic hash of `(path, FRONTEND_BACKEND_API_KEY)` with no expiry or per-user binding, any URL leak (browser history, referrer, shared link, proxy/CDN log) grants indefinite access to that specific file. This is an intentional tradeoff for external-player compatibility, not obviously a bug, but worth flagging as a security/robustness weak point outside pure performance QS.
- **SSR is unlikely to matter for the app's actual streaming hot path (QS-1/QS-3), but does add baseline resource footprint (QS-4)** on every full-page navigation (`/queue`, `/explore/*`, `/settings/*`) even though the UI is entirely behind auth and single-operator. React Router SSR render cost + `@react-router/express` machinery run per navigating request for a UI that has no SEO/first-paint requirement. Given the deployment is a single Docker container on a homelab host (QS-4, QS-7), this is a plausible place where a static SPA build would shed real (if currently unmeasured) memory/CPU relative to keeping an SSR render path alive. **(hypothesis)** — no measurement exists comparing SSR vs SPA resource footprint for this specific app.
- **The websocket relay's `lastMessage` cache is unbounded and per-topic, held in the Node process for the process lifetime** (`websocket.server.ts:9`, `31`) — for this app's small, fixed topic set (queue/history/connections) this is not a practical leak, but it's an in-memory cache that resets on restart, meaning any subscriber connecting during the restart window (QS-5) gets no replayed state until the next backend message arrives.
- **`backend-client.server.ts` repeats the `x-api-key` header construction and `if (!response.ok) throw` boilerplate in all 12 methods** (e.g. lines 5-11, 24-30, 50-56...) with no shared request helper — a maintainability risk (each new endpoint is copy-pasted) rather than a performance one; doesn't affect any QS directly.

## 5. Alternatives brainstorm

| Alternative | QS-7 impact (single-container deployability) | QS impact | Migration cost (recall: architecture is INHERITED) |
|---|---|---|---|
| **Move `/api`, `/view`, `/.ids`, `/nzbs`, `/content`, `/completed-symlinks` proxying out of Express into a lightweight reverse proxy (Caddy/nginx/Traefik) in front of both frontend and backend** | Breaks the current single-container model directly — either a 3rd container/process must be added to the same container (supervisor-managed) or the topology becomes multi-container, which conflicts with the "single local Docker container" deployment target unless carefully bundled (e.g., nginx installed *inside* the same image as a third supervised process). Not free under QS-7. | Improves QS-1/QS-3 modestly: nginx/Caddy's static-file/proxy path has lower per-request overhead than `http-proxy-middleware` in Node and isn't sharing an event loop with SSR rendering — but the existing Express proxy is already not doing buffering/compression on these paths, so the ceiling on improvement is limited to "avoid competing with SSR CPU work," which is itself a hypothesis, not confirmed. Doesn't clearly help QS-4 (adds a process instead of removing one). | High — this is core INHERITED plumbing (`server.ts`, `server/app.ts`, `websocket.server.ts`, `auth-middleware.server.ts` all assume they see every request); a reverse-proxy split would require re-deriving the auth-bypass-for-streaming logic and the websocket upgrade handling entirely outside Node. |
| **Convert to a static SPA (`ssr: false` in `react-router.config.ts`) and drop the custom `createRequestHandler` SSR pipeline, keeping Express only for the proxy + auth + websocket** | Neutral to positive for QS-7 — still one container, likely a lighter one (no SSR render dependencies needed at runtime, `build/client` becomes pure static assets served by `express.static`, already present at `server.ts:82`). | Improves QS-4 (lower baseline CPU/RAM, no per-navigation render) with no realistic downside for QS-1/QS-3 (per the finding above, SSR was never in the streaming path). Neutral-to-positive for QS-5 (less server-side work to boot). **(hypothesis on magnitude)** — the flag exists and is a one-line flip per `react-router.config.ts:6`'s own comment, so this is cheap to literally test. | Low-Medium if attempted — the codebase already anticipates it (`react-router.config.ts` comment), but every route currently written as a `loader` (all data-fetching, e.g. `explore/route.tsx:24-41`, `backend-client.server.ts` consumers) would need to move to client-side `fetch`/React Query-style data loading, and `auth-middleware.server.ts`'s server-side redirect-to-login logic would need a client-side equivalent. This is a real, non-trivial migration despite the one-line config flag. |
| **Different frontend framework entirely (SvelteKit, plain Vite+React SPA, htmx+server templates)** | SvelteKit: similar container story to today (its own Node server or adapter-node), no QS-7 change. Plain Vite+React SPA: simplest single-container story — just static files, Express reduces to proxy+auth+websocket only (same benefit as the SSR-off case above, more so since no framework SSR machinery is loaded at all). htmx+server templates: would let the *backend* (.NET, which already has a real templating/Razor option) own more of the UI directly, potentially eliminating the Node process altogether — the most radical option, matching QS-4/QS-7 best (one runtime instead of two) but the biggest rewrite. | Plain SPA / htmx both plausibly best-case for QS-4 (least JS runtime overhead) and QS-7 (fewest processes, especially htmx-from-backend which could drop Node from the container entirely). SvelteKit doesn't clearly move any QS versus today's React Router setup — same shape of problem, different framework. | Very high for all three — full rewrite of every route (`frontend/app/routes/*`, ~15 route trees) plus, for the htmx option, moving significant UI logic into the backend (.NET) which is a cross-boundary rewrite outside this agent's scope and likely the largest single change discussed in this document. |

## 6. Optimization/improvement candidates

1. **De-duplicate the proxy path list into one shared constant** imported by both `server.ts`'s compression filter and `server/app.ts`'s routing check. QS improved: none directly, but eliminates the "silently breaks seeking or auth for a new path" risk described in Weak Points. Effort: S. Risk: none (pure refactor, no behavior change).
2. **Add a shared `fetchJson` helper in `backend-client.server.ts`** to remove the 12x repeated header/error-handling boilerplate. QS improved: none directly (maintainability only). Effort: S. Risk: low.
3. **Measure SSR vs SPA resource footprint concretely** before deciding on the SPA alternative above: run the container under `docker stats` idle and under a synthetic load (`ab`/`wrk` against `/queue`, `/explore/*`) with `ssr: true` vs `ssr: false`, comparing RSS and CPU. QS improved: informs QS-4 decision-making with real numbers instead of hypothesis. Effort: S (config flag already exists). Risk: none (measurement only, reversible).
4. **Confirm and document the `downloadKey` token's actual verification logic on the backend** (only the frontend half, `getDownloadKey`/`verifyDownloadKey` in `downloads.server.ts`, is in scope here) — specifically whether it has any expiry, since an unbounded capability token is a standing risk regardless of performance QS. Effort: S (backend agent's territory to confirm current behavior). Risk: none to investigate; addressing it (adding expiry) would be M effort and could break long-lived `.strm`-file workflows if not designed carefully.
5. **If pursuing the reverse-proxy alternative, prototype it as an additional supervised process inside the existing single container** (not a topology change) before evaluating further — e.g. Caddy in front of both, still one `docker run`. Effort: M. Risk: M (introduces a new component to keep in sync with backend routes, arguably worse for the "duplicated route list" weak point rather than better, unless the reverse-proxy config becomes the *single* source of truth and Express's own route-matching in `app.ts` is deleted rather than duplicated).

## OPEN QUESTIONS FOR SYNTHESIS

- The actual backend-side verification of `downloadKey` (expiry? per-user scoping? none?) is owned by the API/Auth or core-domain agent — needed to finish item 4 in Optimizations and to fully assess the streaming-auth weak point above.
- Backend route inventory (all `/api/*` and `/Sab*` controllers) should be cross-checked against `backend-client.server.ts`'s method list to confirm there's no drift (frontend calling an endpoint that's been renamed/removed backend-side, or backend endpoints with no frontend caller) — that inventory is the API/Auth agent's territory.
- The core-domain/queue agent's description of `QueueManager`'s websocket broadcast format should be cross-checked against `websocket.server.ts`'s `{Topic, Message}` unwrapping (line 84) to confirm the contract is accurately described here.
- Whether the backend's WebDAV server (`DatabaseStore`/`GetAndHeadHandlerPatch`) does its own internal buffering that would dominate any frontend-proxy-layer latency discussion for QS-1 — if the backend already adds meaningful latency, the frontend-layer optimizations proposed here (items 1, 5) are lower priority than they'd otherwise be.
